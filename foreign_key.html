M5 · Foreign keys

🔗 外部キー — 参照整合性

外部キー（FOREIGN KEY）は「他のテーブルに実在する値だけを許す」制約です。存在しない学生を履修させない——それが参照整合性です。

① 外部キーとは② REFERENCES構文③ エラーと修正④ 教科書の例📝 Quiz
①

外部キーとは何か

他のテーブルの主キーを指す値

外部キー（FOREIGN KEY）とは、あるテーブルの列の値が、別のテーブルの主キー（または一意な列）に実在する値でなければならない、という制約です。

たとえば大学のデータベースで、指導教員（advisor）の担当欄に、実際には在籍していない学生の番号が入ってしまったらどうでしょうか。あるいは、注文レコードの顧客欄に、存在しない顧客IDが入ってしまったら？ どちらも「参照先が実在しない」という同じ問題です。外部キーはこれを防ぎます。

FKとPKの向き
🧑‍🎓
students（親）student_id が主キー（PK）
↑ 参照（FK → PK）
📚
takes（子）student_id が外部キー（FK）
矢印の向きはいつも「子のFK → 親のPK」。takesのstudent_idは、studentsに実在するstudent_idしか受け付けません。
📌 1対多はまったく問題ありません。同じstudent_idがtakesテーブルに何回出てきても構いません——1人の学生は複数の科目を履修するからです。禁止されているのは「親に存在しない値」であって、「重複」ではありません。

大学のスキーマ全体でも、外部キーはあちこちに張られています：takesとadvisorはどちらもstudentsを参照し、teachesはinstructorsを参照し、sectionはcourseとclassroomの2列を同時に参照する複合外部キーを持っています。テーブルが増えるほど、こうした参照の網目がデータベース全体の整合性を支えます。

🍎 かんたん説明

外部キーは「よそのテーブルに実在する値しか入れない」という約束です。矢印はいつも子から親（FK→PK）へ向きます。

②

REFERENCES構文

列制約としてそのまま書ける

外部キーは、主キーと同じく列制約として、データ型のすぐ後ろに書けます。キーワードはREFERENCESです。

-- takes.student_id は students.student_id を参照する
student_id bigint REFERENCES students (student_id)

REFERENCES 参照先テーブル名 (参照先の列名)という並びです。参照先の列は、そのテーブルの主キーか一意な列でなければなりません——そうでなければ「どの行を指しているか」が一意に決まらないからです。

🖥️ pgAdminでの見え方：このテーブルを開いてConstraintsのサブメニューを見ると、主キーのアイコンとは別にForeign-keyの項目が並びます。1つの列に「PKである」「他テーブルのFKである」という2つの性質が同時に付くこともあります。
🍎 かんたん説明

データ型のすぐ後ろに REFERENCES テーブル名 (列名) を書くだけ。参照先は必ずPKか一意な列です。

③

実演：エラーと正しい手順

存在しない学生は履修できない

実際にテーブルを作って試してみましょう。

CREATE TABLE takes (
    student_id bigint REFERENCES students (student_id),
    grade varchar(1)
);
CREATE TABLE Query returned successfully.

studentsにstudent_id = 1, 2, 3が在籍している状態で、まず存在する学生を履修させます。

INSERT INTO takes VALUES (1, 'A');
INSERT 0 1

次に、存在しないstudent_id = 4を履修させようとすると——

INSERT INTO takes VALUES (4, 'B');
ERROR: insert or update on table "takes" violates foreign key constraint "takes_student_id_fkey" DETAIL: Key (student_id)=(4) is not present in table "students".
⚠️ これは事故ではなく、外部キーが正しく仕事をしている証拠です。4番の学生はまだstudentsに存在しないので、「4番の学生の履修記録」を作ることはできません。

修正するには、先に学生本人をstudentsに入学させます（student_idは代理キーなので自動採番されます）。

INSERT INTO students (first_name, last_name, email)
VALUES ('Jane', 'Doe', 'jdoe@example.edu');
INSERT 0 1 （student_id = 4 が自動採番される）

これでstudentsに4番が実在するので、同じINSERTがそのまま成功します。

INSERT INTO takes VALUES (4, 'B');
INSERT 0 1
正しい順番
1️⃣
入学studentsに行を追加
↓
2️⃣
学籍番号発行student_idが自動採番される
↓
3️⃣
履修登録takesにその学籍番号で行を追加
親（students）が先、子（takes）が後。この順序を飛ばすことはできません。
📌 削除は逆向きの同じ問題です。子（takes）から参照されている親（students）の行は、そのままでは削除できません。「先に子を消してから親を消す」か、次のレッスンで学ぶON DELETE CASCADEで自動的に子ごと消すか、どちらかが必要です。
🍎 かんたん説明

親が先、子が後——これがFKの鉄則です。存在しない親を子から指すことはできず、参照されている親を先に消すこともできません。

④

教科書ではこう

licenses と registrations

教科書Practical SQLでは、免許証（licenses）と、その免許に対する更新登録（registrations）の例で外部キーを説明しています。

CREATE TABLE licenses (
    license_id text,
    first_name text,
    last_name text,
    CONSTRAINT licenses_key PRIMARY KEY (license_id)
);

CREATE TABLE registrations (
    registration_id text,
    registration_date timestamp with time zone,
    license_id text REFERENCES licenses (license_id),
    CONSTRAINT registration_key PRIMARY KEY (registration_id, license_id)
);
CREATE TABLE Query returned successfully.

ここでも1対多の関係です——1枚の免許証（licenses）に対して、更新のたびにregistrationsに複数行が積み重なります。さらに注目したいのは、registration_key自体がregistration_idとlicense_idの複合主キーになっている点です。1つの列が「主キーの一部」であると同時に「他テーブルへの外部キー」であってもまったく問題ありません。

📌 外部キーは代理キーにも自然キーにも張れます。参照先が主キーでありさえすれば、その主キーが自動採番の代理キーであっても、免許証番号のような自然キーであっても構いません。
🍎 かんたん説明

1枚の免許証に何回も更新登録がぶら下がる——これも1対多のFKです。複合主キーの一部が同時にFKになることもあります。

💡 学習のヒント

エラーが出たら慌てず「参照先に本当にその値があるか？」を確認しましょう。無ければ先に親を作る——これがFKエラーの99%の直し方です。
