M5 · Types of keys

🗝️ キーの種類を整理する — 候補・スーパー・代替・自然/サロゲート/インテリジェント

「主キー」「外部キー」以外にも、キーには色々な呼び方があります。候補キー・スーパーキー・代替キー・複合キー・合成キー・インテリジェントキー——用語を整理して、なぜその区別が必要なのかを見ていきます。

① 候補キー② スーパーキーと既約性③ 代替キーと外部キー④ 自然キー vs サロゲートキー⑤ 複合・合成・インテリジェントキー📝 Quiz
①

候補キー — 主キーの「候補」たち

どの列が行を一意に識別できるか

アメリカの州を1行ずつ記録するus_statesというテーブルを考えます。列はstate_code（州の郵便略号。例：GA）、state_name（州名）、state_capital（州都）、region（地域）です。

ここで問いを立てます——どの列（またはどの組み合わせ）が、1つの州を絶対に一意に指し示せるか？

state_codeは州の公式な郵便略号で、現実世界で1つの州にしか割り当てられません。しかも安定しています。「GAは明日からミネソタを指すようになる」ということは起こりません。一方、人の携帯電話番号を「その人を識別するID」に使おうとすると危険です。電話番号は変わりうるからです。安定していない値は、良い識別子にはなれません。

state_nameも同じように、州ごとに異なる一意な値です。アメリカの州名がすべて異なることは今後も変わらないと考えてよいでしょう。つまりstate_codeとstate_nameは、どちらも「主キーの候補」になれます。これを候補キー（candidate key）と呼びます。

⚠️ ではstate_capital（州都）は候補キーになれるでしょうか？一見、州都の名前もすべて異なるように見えます。しかし、これはただの「今のところの偶然」です。州は歴史上何度も州都を変更してきました。18世紀後半、ジョージア州の州都はオーガスタ（Augusta）という都市でした。もしジョージア州が将来また州都をオーガスタに戻したら、メイン州の州都もオーガスタなので、2つの州の州都が同じ名前になってしまいます。だからstate_capitalは候補キーではありません。
一意性は「今」だけでなく「未来」も保証できるか
✅
state_code公式な略号。将来も1つの州に1つだけ割り当てられる → 候補キー
↓
✅
state_nameすべての州名が異なる。これも候補キー
↓
❌
state_capital過去に変更された実績あり。将来また重複しうる → 候補キーではない
識別子として使えるかどうかは、「今バラバラかどうか」ではなく「将来もバラバラであり続けるか」で判断する。

2つの候補キー（state_codeとstate_name）のうち、実際にどちらを主キーとして選ぶかは設計者の判断です。今回は単純さの点でstate_codeを選びます。

📌 候補キー（candidate key）とは、主キーの「候補」になれる列（または列の組み合わせ）のこと。候補キーがいくつあっても、実際にPRIMARY KEYとして選ばれるのはそのうち1つだけです。
🍎 かんたん説明

候補キーは「主キーになれる資格を持つ列」全部のこと。その中から1つを選んで、実際の主キーにします。

②

スーパーキーと既約性（irreducibility）

「多すぎる主キー」はなぜダメか

経験の浅い設計者が「一意性を確実にしたい」と思うあまり、必要以上に列を主キーに詰め込んでしまうことがあります。たとえばstate_codeとregionを組み合わせて主キーにしてしまうケースです。

▶ 列を詰め込みすぎた主キー

CREATE TABLE us_states (
    state_code varchar(2),
    state_name text,
    region text,
    CONSTRAINT us_states_pkey PRIMARY KEY (state_code, region)
);
CREATE TABLE

この設計では、次のようなおかしなデータが通ってしまいます。

INSERT INTO us_states (state_code, state_name, region) VALUES
  ('GA', 'Georgia', 'South'),
  ('GA', 'Georgia', 'Southeast');
INSERT 0 2
⚠️ ジョージア州が2行できてしまいました。主キーが(state_code, region)なので、regionさえ違えば同じstate_codeの行を何度でも挿入できてしまいます。これは明らかにおかしい——ジョージア州は1つしかありません。

原因は、この主キーが既約（irreducible）ではないことです。既約とは「一意性を保証するために本当に必要な列だけで構成されている」という意味です。state_codeだけで既に一意なので、regionは本来不要な列です。

(state_code, region)のように、一意性は保証するが、余計な列を含んでいるものをスーパーキー（super key）と呼びます。候補キーは「既約なスーパーキー」——つまり無駄のないスーパーキーのことです。

用語定義今回の例
スーパーキー一意性を保証する列（の集合）。余計な列を含んでもよい(state_code, region)
候補キー既約なスーパーキー。無駄な列がないstate_code / state_name
📌 スーパーキーという用語は普段のSQL設計ではあまり使いません。ボイス・コッド正規形（BCNF）など、正規化の厳密な定義の中で登場する概念です。ここで大事なのは「候補キーを選ぶときは、必要最小限の列だけにする」という実務上の教訓です。
🍎 かんたん説明

主キーに列を足しすぎると、かえって重複を防げなくなることがあります。「一意にするために本当に必要な列だけ」を選ぶのが既約＝候補キーの条件です。

③

代替キー（alternate key）と外部キーのつながり

選ばれなかった候補キーはどうなるか

state_codeを主キーに選んだので、もう片方の候補キーだったstate_nameはどうなるでしょうか。主キーは1つのテーブルに1つしか作れないので、state_nameを主キーにすることはできません。しかし、state_nameもやはり「重複してはいけない」列です。

▶ state_nameの一意性もUNIQUE制約で守る

CREATE TABLE us_states (
    state_code varchar(2) PRIMARY KEY,
    state_name text UNIQUE,
    state_capital text,
    region text
);
CREATE TABLE
📌 これが代替キー（alternate key）です。候補キーではあるものの、主キーには選ばれず、代わりにUNIQUE制約で一意性だけを保証される列のことを代替キーと呼びます。

次に、us_statesを参照するvoters（有権者）テーブルを作ります。有権者の登録州が、実在する州でなければならない——という制約を外部キーで表現します。

▶ voters.state_of_registrationはus_states.state_codeを参照する

CREATE TABLE voters (
    voter_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    voter_name text,
    state_of_registration varchar(2) REFERENCES us_states (state_code)
);
CREATE TABLE
INSERT INTO voters (voter_name, state_of_registration)
VALUES ('Jane Doe', 'QX');
ERROR: insert or update on table "voters" violates foreign key constraint "voters_state_of_registration_fkey" DETAIL: Key (state_of_registration)=(QX) is not present in table "us_states".

QXという州コードはus_statesに存在しないので、外部キー制約がこの行を拒否します。こうして候補キー・主キー・外部キーが連携し、テーブル同士のデータの整合性を守っています。

🍎 かんたん説明

候補キーが2つあっても、主キーになれるのは1つだけ。もう1つはUNIQUE制約付きの「代替キー」として一意性を守ります。

④

自然キー vs サロゲートキー — 見分け方をもう一段深く

「現実世界で意味を持つか」がすべて

PK②のレッスンで、自然キーと代理キー（サロゲートキー）の違いには軽く触れました。ここでは、その見分け方の本質をもう少し掘り下げます。

us_statesを、州コードの代わりに自動採番のstate_idを主キーにした設計に変えてみましょう。

CREATE TABLE us_states (
    state_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    state_code varchar(2) UNIQUE,
    state_name text UNIQUE
);
CREATE TABLE

この設計でvotersとJOINするときも、state_codeで結合していた部分をstate_idに変えるだけで、同じ結果が得られます。つまりJOINできるかどうかという点では、state_codeのような「意味のある値」でもstate_idのような「意味のない連番」でも、どちらでも構いません。

📌 本当の見分け方はこれです——「その値は、データベースの外の現実世界でも意味を持つか？」州コードGAは、データベースを知らない人でも「ジョージア州のことだ」と分かります。これが自然キー（natural key／business keyとも呼ばれます）です。一方state_id = 25は、このデータベースの中でしか意味を持ちません。これが代理キー（surrogate key）です。

自然キーの他の例：マイナンバーや社会保障番号のような国のID、メールアドレス、保険会社から届く手紙に書かれている顧客番号——これらはすべて、現実世界で人が実際に使う識別子なので自然キーです。

⚠️ 自然キーか代理キーかは、「公開されているかどうか」で変わることがあります。ISBN（国際標準図書番号）は書籍の自然キーですが、電子書籍（ebook）にはISBNが付いていないことが多く、オンライン書店のbooksテーブルの主キーには使えません。代わりに自社で発行するbook_numberを作ることになります。もしこのbook_numberを商品ページに表示して一般公開すれば、それはもう代理キーではなく自然キーになります。逆に社内でしか使わない番号なら、代理キーのままです。

代理キーには注意すべき落とし穴もあります。代理キーの仕事は「単に行にIDを振ること」ではなく、「現実世界の1つの物事を正しく1つの行に対応させること」です。

state_idstate_codestate_name
1MAMassachusetts
2MAMassachusetts
⚠️ この2行はstate_idが違うので「別の行」として保存できてしまいますが、どちらもマサチューセッツ州です。代理キーはここでは何の役にも立ちません。これを防ぐには、state_codeやstate_nameにUNIQUE制約（代替キー）を付けておく必要があります。
🍎 かんたん説明

見分け方は1つだけ——「データベースの外でもその値に意味があるか」。あるなら自然キー、ないなら代理キーです。

⑤

複合キー・合成キー・インテリジェントキー

複数の部品でできたキーたち

主キーは1列とは限りません。カフェのメニューを考えます。coffee_type（コーヒーの種類）とcup_size（サイズ）を組み合わせて初めて、1つのメニュー項目が一意になります。

CREATE TABLE coffee_options (
    coffee_type text,
    cup_size text,
    price numeric(5,2),
    CONSTRAINT coffee_options_pkey PRIMARY KEY (coffee_type, cup_size)
);
CREATE TABLE

1列だけの主キーを単純キー（simple key）、2列以上の主キーを複合キー（composite key）と呼びます。これは以前のレッスン（PK②）で学んだ通りです。

⚠️ ここに、もう1つ細かい用語があります——合成キー（compound key）。「合成キー」を「複合キー」とまったく同じ意味で使う人もいますが、人によっては「複合キーの中でも、すべての列がそれぞれ他テーブルへの外部キーになっているもの」だけを合成キーと呼びます。たとえば顧客と口座を多対多で結ぶcustomer_accountsテーブルがそうです。
CREATE TABLE customer_accounts (
    customer_id bigint REFERENCES customers (customer_id),
    account_id bigint REFERENCES accounts (account_id),
    CONSTRAINT customer_accounts_pkey PRIMARY KEY (customer_id, account_id)
);
CREATE TABLE

customer_idもaccount_idも、それぞれ別テーブルへの外部キーです。この2つを組み合わせた主キーは、複合キーであると同時に、この意味では合成キーでもあります。

最後に、もう1種類——インテリジェントキー（intelligent key）です。玩具メーカーの商品コードを例にします。CLS-TRN-016のように、「カテゴリ（Classic）」「サブカテゴリ（Train Sets）」「連番（016）」の3つの意味のある部品をつなげて作った自然キーです。

CLS-TRN-016 の分解
1️⃣
CLS商品カテゴリ：Classic（クラシック）
→
2️⃣
TRNサブカテゴリ：Train Sets（鉄道模型）
→
3️⃣
016連番：このサブカテゴリの16番目の商品
意味のある部品をくっつけて1つの自然キーにしたものが、インテリジェントキー。
⚠️ インテリジェントキーには落とし穴があります。①誰かが「商品コードの真ん中を見ればサブカテゴリが分かる」と考えて、コードから文字列を切り出してレポートを作ってしまうことがあります。これは商品コードの書式が変わった瞬間に壊れます——サブカテゴリは必ず専用の列にきちんと記録し、そちらを使うべきです。②商品の分類方法自体を変えたくなったとき（例：Classic/Modernから電池式/非電池式へ）、既存の商品コードの書式と矛盾してしまい、大規模な修正が必要になることがあります。
📌 インテリジェントキーを禁止する必要はありませんが、部品の選び方が大切です。安全な例としては、顧客の生年月日＋連番（例：1997.0308.0096）のように、絶対に変わらない情報を部品に選ぶと、書式が壊れる心配がほとんどありません。
🍎 かんたん説明

複合キー＝2列以上の主キー。合成キーはその中でも「全列が外部キー」の場合を指すことがある呼び方。インテリジェントキーは「意味のある部品をつなげた自然キー」——ただし分類が変わると壊れやすい点に注意。

📖 用語集

候補キー
candidate key
主キーの候補になれる、既約で常に一意な列（の組み合わせ）。
スーパーキー
super key
一意性を保証するが、余計な列を含んでいてもよい列の集合。
代替キー
alternate key
候補キーではあるが主キーに選ばれず、UNIQUE制約で一意性だけ守る列。
自然キー（業務キー）
natural key / business key
データベースの外の現実世界でも意味を持つ値を使う主キー。
合成キー
compound key
全列がそれぞれ外部キーになっている複合キーを指す、より厳密な呼び方。
インテリジェントキー
intelligent key
意味のある部品をつなげて作った自然キー。分類変更に弱い。
