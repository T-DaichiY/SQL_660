M5 · Naming conventions

📝 命名規則 — snake_caseと引用識別子

テーブル名・列名は自由に付けられますが、自由すぎると後で自分が困ります。PostgreSQLの世界の「決まりごと」を押さえておきましょう。

① 3つのケース② 小文字化と引用識別子③ 命名の指針5か条📝 Quiz
①

3つのケース（命名スタイル）

同じ単語列でも書き方が違う

「イチゴのスムージー」を変数名にするとしたら、あなたはどう書きますか？　実は英語圏のプログラミングでは、複数の単語を1つの識別子にまとめる書き方が何通りかあり、それぞれに名前が付いています。

🐫
camelCase
berrySmoothie
🏛️
PascalCase
BerrySmoothie
🐍
snake_case
berry_smoothie

camelCaseは最初の単語だけ小文字で始め、以降の単語の頭を大文字にします（ラクダのこぶのように見えることから）。PascalCaseはすべての単語の頭を大文字にします。snake_caseはすべて小文字にして、単語の間をアンダースコアでつなぎます（アンダースコアが蛇のように見えることから）。

T-SQL（SQL Server）やMicrosoftのドキュメントでは伝統的にPascalCase寄りの命名がよく見られますが、PostgreSQLの公式ドキュメントやコミュニティの慣習は一貫してsnake_caseを推奨しています。この講座では以降、テーブル名・列名はすべてsnake_caseで統一します。

📌 良い名前の3条件——specific（具体的）・concise（簡潔）・consistent（一貫している）。この3つのCを意識するだけで、命名の8割は解決します。
🍎 かんたん説明

書き方は3通りあるけど、PostgreSQLではsnake_case（全部小文字＋アンダースコア）が基本です。

②

PostgreSQLは小文字にそろえる・引用識別子

Customers と customers は同じテーブル

PostgreSQLには、他のDBMSにはない大きな癖があります。クォートなしで書いた識別子（テーブル名・列名）は、内部的にすべて小文字へと自動的に変換されるのです。つまりCustomersと書いてもcustomersと書いても、PostgreSQLにとっては全く同じテーブルを指します。

-- 1回目：問題なく作成される
CREATE TABLE customers (
    customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_name text
);
CREATE TABLE Query returned successfully.
-- 2回目：先頭を大文字にしただけのつもり…
CREATE TABLE Customers (
    customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_name text
);
ERROR: relation "customers" already exists

PostgreSQLはCustomersを小文字化してcustomersとして扱うため、「すでに存在するテーブルをもう一度作ろうとした」というエラーになります。大文字・小文字の違いはPostgreSQLにとって意味を持ちません。

引用識別子（quoted identifier）

もしどうしても大文字・小文字を区別したい、あるいはスペースを含む名前や予約語を使いたい場合は、識別子を二重引用符（"）で囲むことができます。これを引用識別子と呼びます。

-- 二重引用符で囲むと別のテーブルとして作れる
CREATE TABLE "Customers" (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);
CREATE TABLE Query returned successfully.

これでcustomersと"Customers"は別々のテーブルとして共存します。しかし代償があります——一度引用符付きで作った識別子は、それ以降このテーブルを参照するたびに毎回引用符が必要になります。

-- 引用符を忘れると別テーブル（customers）を見てしまう、または見つからない
SELECT * FROM "Customers";   -- OK：引用符あり
SELECT * FROM Customers;     -- これは customers を見てしまう
⚠️ 引用識別子は「例外」として使うべきです。スペースを含む名前や予約語（"table"や"order"など）をどうしても使わざるを得ない場合、あるいはT-SQLの一部の慣習を踏襲する場合に限り、チーム内でルールを決めた上で使いましょう。日常的に使うと、参照のたびに引用符の付け忘れでエラーやバグを招きます。
🍎 かんたん説明

クォートなしの名前はPostgreSQLが勝手に小文字にします。大文字を区別したいなら"引用符"が要りますが、毎回付け忘れると事故のもとです。

③

命名の指針5か条

未来の自分と同僚を助けるルール

大学のデータベース（students / takes / advisor / classroom …）を例に、実務でよく使われる命名の指針を5つ紹介します。

指針内容例
① snake_caseすべて小文字＋アンダースコア区切りarrival_time（○）／ArrivalTime（✗）
② 分かりやすさ省略しすぎず、意味が伝わる名前にarv_tm（✗）→ arrival_time（○）
③ テーブル名は複数形1行=1件のデータなので、集合を表す複数形が基本teachers（○）。ただし大学DBのcourseは単数形の反例
④ 長さの制限DBMSごとに識別子の最大長があるPostgreSQLは63バイトまで（それ以降は自動的に切り詰められる）
⑤ コピーには日付をバックアップ・複製テーブルには作成日を付けるvehicle_parts_2021_04_08

③の反例として、大学DBでは「1つの科目」を表すテーブルに、複数形のcoursesではなく単数形のcourseを使っているケースがあります。指針はあくまで指針であり、プロジェクト内で一貫していることの方が優先されます。

命名規則が無いと、こうなる

同じ「顧客データ」のつもりで作られたテーブル群（実在のプロジェクトでありがちな例）

❓
Customers
最初に作った本体？
❓
customers
誰かが作り直した？
❓
custBackup
いつのバックアップ？
❓
customer_analysis
分析用の一時テーブル？
❓
customer_test2
test1はどこ？
❓
customeranalysis
上の別バージョン？単語の区切りすら不明
どれが本物で、どれが古いバックアップで、どれが消してよいものか——名前だけでは誰にも分かりません。
📓 大学DBではstudentsにもadvisorにもidという列がよく出てきます。すべて同じ「id」という名前だと、JOINしたときや会話の中で「どのid？」と混乱します。テーブル名を接頭辞にしたstudent_id・advisor_idのように名付ければ、どのテーブルのキーなのかが名前だけで分かります。
🍎 かんたん説明

snake_case・分かりやすさ・複数形・長さ・日付付きコピー——この5つを守れば、半年後の自分も同僚も迷いません。

📖 用語集

identifier
識別子
テーブル名・列名など、データベースオブジェクトを指す名前。
snake case
スネークケース
すべて小文字にし、単語間をアンダースコアでつなぐ命名法。PostgreSQL推奨。
quoted identifier
引用識別子
二重引用符で囲んだ識別子。大文字小文字・スペース・予約語を許すが、参照のたびに引用符が必要。
reserved keyword
予約語
SELECTやtableのように、SQL自体が意味を持たせている語。識別子に使うには引用符が要る。
plural table names
複数形のテーブル名
1行=1件を表すため、テーブル名は複数形にするのが一般的な慣習（例外もある）。
