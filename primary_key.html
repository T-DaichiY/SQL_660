M5 · Primary keys Part 1

🔑 主キー① — 制約とは・自然キー

主キーは「この行を一意に指し示す列」です。まずは制約という考え方全体を押さえてから、主キーの2つのルールと3種類のキーを見ていきます。

①

制約とは何か

入力データに枠をはめる仕組み

制約（constraint）とは、テーブルに入れられるデータを制限するルールです。「どんな値でも自由に入れられる」テーブルは、一見便利に見えて、実はとても壊れやすいものになります。

Googleフォームでアンケートを作るときのことを思い出してください。「Tシャツのサイズ」を自由記述にすると、「M」「medium」「ミディアム」「えむ」がバラバラに集まってしまいます。「電話番号」を自由記述にすると、ハイフンあり・なし・国番号あり・なしが混在します。「メールアドレス」も、@すら入っていない回答が紛れ込むことがあります。だからGoogleフォームには、選択式・電話番号形式・メール形式といった入力の型が用意されているのです。

データベースの制約もまったく同じ発想です。garbage in, garbage out（ゴミを入れればゴミしか出てこない）——制約は、この「ゴミ」がテーブルに入るのを、そもそも入り口で防ぐための仕組みです。

制約は何層にも重なる
1️⃣
データ型そもそも最初の制約。numeric列に文字は入らない
↓
2️⃣
キー（PK・FK）行を一意に識別し、テーブル同士のつながりを保証する
↓
3️⃣
CHECK / NOT NULL / UNIQUE値の範囲・必須入力・重複禁止をさらに細かく指定する
このレッスンでは②の「キー」、なかでも主キー（PRIMARY KEY）を扱います。①のデータ型はM1〜M2、③はこの後のレッスン「制約」で扱います。
📌 制約はテーブル設計の要です。後から直すより、最初から正しい制約を付けておくほうがずっと楽です。
🍎 かんたん説明

制約＝「変な値を入れさせない仕組み」。Googleフォームの入力形式と同じ発想です。

②

主キーの2ルールと3種類

一意であること・NULLでないこと

主キー（PRIMARY KEY, PK）は、テーブルの各行を一意に識別する列（または列の組み合わせ）です。主キーには、絶対に破ってはいけない2つのルールがあります。

主キーの2ルール
  1. 一意である（unique）——同じ値を持つ行が2つ以上あってはならない
  2. NULLを許さない（not null）——値が空の行があってはならない

この2ルールを満たす列の選び方には、大きく3つのパターンがあります。

種類特徴例
自然キー
natural key		もともと業務データの中にある、意味を持った値免許証番号、course_id、学籍番号、email
代理キー
surrogate key		意味を持たず、DBが自動的に振る連番など自動採番のID、UUID
複合キー
composite key		1列だけでは一意にならないとき、複数列を組み合わせる免許証番号＋州、room_number＋building
🪪
自然キー
免許証番号 / email
🔢
代理キー
自動採番ID / UUID
🧩
複合キー
免許証番号＋州

なぜ複合キーが必要になることがあるのでしょうか。教科書に出てくる、アメリカの運転免許証番号の例で考えてみます。

driver_idstatename
10302019NYAdams, Bill
10302019FLReyes, Maria

アメリカでは免許証番号は州ごとに発行されるため、driver_idだけを見ると同じ10302019という番号が、まったくの別人に対して2回登場してしまいます。これではdriver_id単独は主キーの「一意」ルールを満たせません。しかしdriver_id + stateの組み合わせなら、この2行は別の値になり、一意性が保たれます。これが複合キーが必要になる典型的な理由です。

⚠️ 代理キーはUUIDでも作れますが、注意が必要です。UUIDは値が長く（128ビット）、テーブルが巨大になると容量やインデックスの効率で不利になることがあります。単純な連番で十分なら、bigintの自動採番のほうが軽量です（詳しくは次のレッスン「PK②」）。
🍎 かんたん説明

主キーは「重複なし・空欄なし」。データ自身に使える値があれば自然キー、なければ自動採番の代理キー、1列で足りなければ複合キー。

③

構文：列制約とテーブル制約

同じ主キーでも書き方は2通り

主キーを宣言する方法には、列制約（column constraint）とテーブル制約（table constraint）の2通りがあります。まず、列の定義に直接くっつける「列制約」の書き方です。

-- 列制約：列の定義の直後に書く
CREATE TABLE course (
    course_id varchar(8) CONSTRAINT course_key PRIMARY KEY,
    course_name varchar(100)
);
CREATE TABLE Query returned successfully.

次に、すべての列を書き終えたあとに、まとめて宣言する「テーブル制約」の書き方です。結果はまったく同じテーブルになります。

-- テーブル制約：全ての列の後にまとめて書く
CREATE TABLE course (
    course_id varchar(8),
    course_name varchar(100),
    CONSTRAINT course_key PRIMARY KEY (course_id)
);
CREATE TABLE Query returned successfully.
📌 CONSTRAINT 名前の部分は省略できます。省略すると、PostgreSQLが自動的にテーブル名_pkey（この例ではcourse_pkey）という名前を付けてくれます。最短形はこれだけです。
-- 最短形：名前を付けず、列制約だけで済ませる
course_id varchar(8) PRIMARY KEY

実際に付いた制約は、pgAdminのツリーで テーブル名 → Constraints のサブメニューを開くと確認できます。ここに主キーの名前と対象列が表示されます。

主キーに指定した列は、宣言にNOT NULLと書いていなくても、自動的にNOT NULLになります。これは「主キーはNULLを許さない」という2ルール目が、PostgreSQL側で自動的に強制されるためです。
🍎 かんたん説明

列制約は「その場で1行」、テーブル制約は「最後にまとめて1行」。どちらも同じ主キーを作れます。名前は省略可能です。

④

重複を入れてみる

主キーが実際に守ってくれる様子を見る

教科書の例にならって、免許証番号を自然キーとするテーブルを作ってみます。

CREATE TABLE natural_key_example (
    license_id text CONSTRAINT license_key PRIMARY KEY,
    first_name text,
    last_name text
);
CREATE TABLE Query returned successfully.

まず1行目を入れます。問題なく入ります。

INSERT INTO natural_key_example (license_id, first_name, last_name)
VALUES ('T229901', 'Gem', 'Godfrey');
INSERT 0 1

次に、同じ免許証番号で別人をもう1行入れようとすると、どうなるでしょうか。

INSERT INTO natural_key_example (license_id, first_name, last_name)
VALUES ('T229901', 'John', 'Mitchell');
ERROR: duplicate key value violates unique constraint "license_key" DETAIL: Key (license_id)=(T229901) already exists.
⚠️ これが主キーの本当の役割です。「T229901というJohn Mitchellがすでにいる」ことをPostgreSQL自身が検出し、挿入を拒否しました。もしこの列に主キーが付いていなければ、この重複はそのままテーブルに入ってしまい、後で「T229901は誰なのか」を特定できなくなっていたはずです。
📌 エラーメッセージの"license_key"という部分は、私たちがCONSTRAINT license_key PRIMARY KEYで付けた名前がそのまま使われています。名前を省略していれば、ここは"natural_key_example_pkey"と表示されていました。
🍎 かんたん説明

同じ主キーの値を2回入れようとすると、PostgreSQLはエラーで止めてくれます。これが「一意性」を守る仕組みです。
