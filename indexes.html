①

インデックス＝本の索引

B-treeはPostgreSQLの既定インデックス

分厚い本で特定の単語を探すとき、最初のページから1枚ずつめくる人はいません。巻末の索引（index）でページ番号を引けば一瞬です。データベースのインデックスも同じ発想で、テーブル本体とは別に「値 → 行の場所」を整理した構造を用意しておき、検索のたびに全行を読まずに済むようにします。

PostgreSQLでは、PRIMARY KEYやUNIQUE制約を付けた列に、自動的にインデックスが作られます。既定のインデックスの種類はB-tree（B木）で、特別な指定をしなければこれが使われます。

索引が無ければ、本もDBも「全部めくる」しかない
📖
索引のない本「B-tree」という語を探すため、1ページ目から順にめくる
↓
📑
巻末の索引を引く「B-tree → 214ページ」とすぐ分かる
↓
🗄️
インデックスの無いテーブル1行目から順に全部読む＝Sequential Scan（順次スキャン）
↓
⚡
インデックスのあるテーブル目的の行だけ直接たどれる＝Index Scan（索引スキャン）
本の索引が「ページ番号の目次」であるように、DBのインデックスは「値と行の対応表」。

B-treeが得意な条件・苦手な条件

-- ○ B-treeが得意：等号・比較・範囲
SELECT * FROM new_york_addresses WHERE street = 'BROADWAY';
SELECT * FROM new_york_addresses WHERE zip_code BETWEEN 10001 AND 10010;
-- ○ 先頭にワイルドカードが無いLIKEもOK
SELECT * FROM new_york_addresses WHERE street LIKE 'Dorito%';
-- ✗ 先頭がワイルドカードだとB-treeを使えない
SELECT * FROM new_york_addresses WHERE street LIKE '%dorito';
📌 B-treeが効くのは= < <= > >= BETWEENのような等号・範囲の比較、そしてLIKE 'Dorito%'のように先頭が具体的な文字で始まるパターンです。LIKE '%dorito'のように先頭がワイルドカードの場合、索引の並び順を使って絞り込む方法がないため、B-treeは活躍できません。
🍎 かんたん説明

インデックスは本の索引と同じ。PRIMARY KEYやUNIQUEを付けると、PostgreSQLがB-treeという索引を自動で作ってくれます。

②

EXPLAIN ANALYZEで測る

94万行のnew_york_addressesテーブル

教科書のサンプルデータには、ニューヨーク市の住所データnew_york_addressesがあります。行数はおよそ94万行。「速くなった」を感覚ではなく数字で確認するために、EXPLAIN ANALYZEを使います。これはクエリを実際に実行し、どういう手順で処理されたか・実際に何ミリ秒かかったかを表示するコマンドです。

EXPLAIN ANALYZE
SELECT * FROM new_york_addresses WHERE street = 'BROADWAY';
Parallel Seq Scan on new_york_addresses (cost=0.00..21759.00 rows=1 width=127) (actual time=0.842..380.115 rows=118 loops=3) Filter: (street = 'BROADWAY'::text) Rows Removed by Filter: 313333 Planning Time: 0.146 ms Execution Time: 389.232 ms

1行目のParallel Seq Scan on new_york_addressesに注目してください。Seq Scan（Sequential Scan＝順次スキャン）とは、テーブルの全行を1行ずつ読んで条件に合うかどうかを調べる方式です。インデックスがまだ無いので、94万行すべてをチェックするしかありません。最後の行Execution Time: 389.232 msが、実際にかかった時間です。

⚠️ インデックスが無い列を条件にすると、テーブルが大きいほどWHEREは遅くなります。94万行なら389ミリ秒。行数がさらに増えれば、この時間も比例して伸びていきます。
🍎 かんたん説明

EXPLAIN ANALYZEは「実際に実行して、かかった時間を教えてくれる」コマンド。Seq Scanは全行チェックなので遅くなりがちです。

③

CREATE INDEXで速くする

389msが5msになる

それではstreet列にインデックスを作ってみます。構文はシンプルです——どのテーブルの・どの列に・何という名前で作るかを指定するだけです。

CREATE INDEX street_idx ON new_york_addresses (street);
CREATE INDEX

同じEXPLAIN ANALYZEクエリをもう一度実行します。

EXPLAIN ANALYZE
SELECT * FROM new_york_addresses WHERE street = 'BROADWAY';
Bitmap Heap Scan on new_york_addresses (cost=4.68..1287.65 rows=354 width=127) (actual time=0.038..4.985 rows=354 loops=1) Recheck Cond: (street = 'BROADWAY'::text) Heap Blocks: exact=352 -> Bitmap Index Scan on street_idx (cost=0.00..4.59 rows=354 width=0) (actual time=0.029..0.029 rows=354 loops=1) Index Cond: (street = 'BROADWAY'::text) Planning Time: 0.092 ms Execution Time: 5.113 ms

今度は一番下の行にあるBitmap Index Scan on street_idxに注目です。94万行を1行ずつ読む代わりに、索引を使って該当行だけを直接見つけています。結果、Execution Timeは389.232 ms → 5.113 ms——約76倍の高速化です。

クエリの条件（教科書 Table 8-1）インデックス前インデックス後
WHERE street = 'BROADWAY'92 ms5 ms
WHERE street = '52 STREET'94 ms1 ms
WHERE street = 'ZWICKY AVENUE'93 ms1 ms未満

不要になったインデックスはDROP INDEXで削除できます。

DROP INDEX street_idx;
DROP INDEX
📌 インデックスを作っても、書いたSQLは1文字も変わっていません。SELECT * FROM new_york_addresses WHERE street = 'BROADWAY'はそのまま。速くなったのは、PostgreSQLが裏側でstreet_idxを見つけて自動的に使ってくれたからです。
🍎 かんたん説明

CREATE INDEX 名前 ON テーブル(列)を実行するだけ。クエリ自体は変えなくても、PostgreSQLが自動でインデックスを使い、劇的に速くなります。

④

使いどころと注意点

どこにでも付ければいいわけではない

インデックスを付けると良いのは、主に次の2種類の列です。

列の種類インデックスが有効な理由
JOINで使う列主キーには自動でインデックスが付くが、参照する側（外部キー）の列には自動で付かないため、自分で作ると結合が速くなる
WHEREでよく使う列頻繁に検索条件になる列は、インデックスによる恩恵が大きい
-- 外部キー列は自動でインデックスされない → 自分で作る
CREATE TABLE takes (
    student_id bigint REFERENCES students (student_id) ON DELETE CASCADE,
    course_id varchar(8),
    grade varchar(1)
);
CREATE INDEX takes_student_id_idx ON takes (student_id);
📌 外部キー列にインデックスを付けておくと、ON DELETE CASCADEで親を削除したときの「子の行を探す処理」も速くなります。削除のたびにtakesを全行スキャンせずに済むからです。

一方で、インデックスはタダではありません。

⚠️ インデックスは容量を食い、書き込みのたびにメンテナンスが必要です。1行INSERT・UPDATE・DELETEするたびに、テーブル本体だけでなくすべてのインデックスも更新しなければなりません。列という列に片っ端からインデックスを付けると、検索は速くなっても書き込みが重くなり、ディスク容量も増えていきます。
📌 「付けるべきか」を勘で決めない。本当に効果があるかはEXPLAIN ANALYZEで実測してから判断します。使われていないインデックスはDROP INDEXで外すのも、テーブル設計の一部です。
🍎 かんたん説明

JOINやWHEREでよく使う列にはインデックスが効きます。ただし書き込みコストと容量が増えるので、全部の列に付けず、EXPLAIN ANALYZEで確かめてから決めましょう。

index
インデックス（索引）
値と行の場所を対応づけた別構造。全行を読まずに検索できるようにする。
B-tree
B木
PostgreSQLの既定インデックス型。等号・範囲比較・先頭一致のLIKEに強い。
EXPLAIN ANALYZE
実行計画＋実測時間

sequential scan
順次スキャン

index scan
索引スキャン
インデックスを使い、該当する行だけを直接たどる方式。
