🗄️ リレーショナルデータベース入門

①

データベースはどう使われているか

データウェアハウジング vs OLTP

決済処理、航空会社の予約、オンライン広告、SNS、学校の校務システム——データベースの用途は数え切れません。しかしその根っこにあるのはシンプルな考え方です。データベースとは情報を保存する仕組みであり、複数の人が同時にアクセスできる場所にデータを置いておき、そこから必要なものを取り出したり書き込んだりします。それを組織的に管理する仕組みがDBMS（Database Management System／データベース管理システム）です。

用途を大きく2つに分けると、次のようになります。

用途何をするか具体例
データウェアハウジング
（Data Warehousing）		大量のデータを蓄積・保存しておき、後で分析や参照に使うSNSが投稿や行動データを蓄積し、後からアプリで表示する
オンライントランザクション処理
（OLTP）		取引（トランザクション）をその場で処理し、結果を記録するAmazonでの注文処理、注文番号からの照会

情報を集めたり保存したりするソフトウェアは、突き詰めればこの2つのどちらか（あるいは両方）を行っています。SNSも、投稿データを蓄積する（データウェアハウジング）と同時に、あなたがアプリを開いたときにその情報を返す（OLTP的な読み出し）という両方の役割を担っています。

📌 この用途の違いが、どのデータベースモデルを選ぶかに直結します。「データをどう蓄積し、どう取り出したいか」によって、最適なDBMSの種類は変わってきます。次のユニットで、その選択肢を見ていきましょう。
🧭 この先のM6モジュールでは、University（大学）サンプルデータベースを使います。pgAdminで新しいデータベースを作成し、テーブル構造（主キー・外部キー・データ型）を定義するDDLスクリプトをクエリツールで実行してテーブルを作成、続けてデータファイル（SQL形式のINSERT文）を実行してレコードを流し込む、という2段階でインポートします。まだの人は、セットアップ動画で先にインポートを済ませておきましょう。
🍎 かんたん説明

データベースの使い道は大きく2つ。「ためておく」データウェアハウジングと、「その場で処理する」OLTP。SNSもネットショップも、この組み合わせでできています。

💻 ミニ練習：インポートした行数を確認する

University DBを読み込んだあと、studentテーブルに何行あるか確認したいです。行数を1つの数値として返すSQLを書いてください。

SELECT count(*) FROM student;

count(*)は「行数を数える」集計関数です（M4で学習済み）。

②

データベースモデルの種類

階層型・ネットワーク型・オブジェクト指向型・リレーショナル型

DBMSにはいくつかの「モデル（構造の型）」があります。代表的な4種類を見てみましょう。

モデル構造のイメージ特徴
階層型
Hierarchical		組織図のようなツリー構造。頂点に親、その下に子各子は1つの親としか繋がらない。上から下へ一方向に広がる構造
ネットワーク型
Network		階層型を拡張した構造子が複数の親を持てる（例：「店員」と「顧客」がどちらも「取引」の親になる）。階層型より柔軟
オブジェクト指向型
Object-Oriented		プログラミングの「オブジェクト」と同じ発想データと、それに対する操作（メソッド）をひとまとめの「オブジェクト」として扱い、オブジェクト同士が連携する
リレーショナル型
Relational		複数の表（テーブル）の集まりExcelのブックが複数のシートを持ち、セル参照で繋がるのに似ている。テーブル同士を主キー・外部キーで関連づける

リレーショナルモデルを直感的に理解するには、Excelを思い浮かべると分かりやすいです。1つのワークブックに「シート1」と「シート2」があり、シート2のセルで=シート1!A1のように参照すると、シート1の値が変わればシート2の表示も自動的に更新されます。リレーショナルデータベースも同じで、あるテーブルの値を別のテーブルから参照できます。その仕組みを支えるのが主キー（Primary Key／PK）と外部キー（Foreign Key／FK）——テーブル同士を結びつける、一意な値です（詳しくはM5で扱った通りです）。

これらのモデルにはそれぞれ強みと弱みがあり、優劣が一律に決まるわけではありません。ただし、SQLを使うRDBMS（Relational Database Management System／関係データベース管理システム）は長年デファクトスタンダードとされてきました。近年は他のモデル（特にNoSQL）も人気を集めていますが、多くの有名サービスは今もRDBMSの上に構築されているか、少なくとも重要な役割を担っています。大企業ほど、用途に応じて複数のモデルを併用しているケースも珍しくありません——「全部SQL」である必要はないのです。

🍎 かんたん説明

階層型は「親は1人」、ネットワーク型は「親は複数OK」、オブジェクト指向型は「データ＋操作をセットで扱う」、リレーショナル型は「表同士をキーで繋ぐ」。今学んでいるのはこの最後、リレーショナル型です。

💻 ミニ練習：主キーを持つテーブルを作る

book_id（整数・主キー）とtitle（文字列）を持つbookテーブルを作るSQLを書いてください。主キーがあるからこそ、後から他のテーブルの外部キーで参照できます。

CREATE TABLE book (
    book_id integer PRIMARY KEY,
    title text
);

主キー制約があるおかげで、book_idの重複やNULLがデータベース側で防がれます。

③

ACID特性

RDBMSが「壊れにくい」理由

リレーショナルモデルは非常に構造的で厳格です。先生はよく「SQLはデータベース界のJavaのようなもの」と表現します——ルールが厳しく型もきっちり決まっている分、その代わりに強力な保証が得られるのです。その保証をまとめた頭文字がACIDです。ACIDは、RDBMSにおける各トランザクション（1回の処理のまとまり）が満たすべき4つの性質を表しています。

ACID＝トランザクションを守る4つの性質
🧩
Atomicity（原子性）トランザクションは「全部成功」か「全部失敗」のどちらか。一部だけ実行される中途半端な状態は存在しない
↓
✅
Consistency（一貫性）トランザクションが完了したとみなされる前に、変更が確実に反映される。データは常に矛盾のない状態を保つ
↓
🔒
Isolation（独立性）複数のトランザクションは互いに干渉されず独立して実行される。同時アクセスによる衝突を防ぐ
↓
💾
Durability（永続性）一度コミット（確定）されたトランザクションは失われない。中途半端な形で保存されることもない
この4つが揃っているからこそ、銀行の取引のような「絶対に間違えられない」処理を安心して任せられます。

原子性（Atomicity）は「all or nothing」——SQLで何かコマンドを実行するとき、その一部でも失敗すれば、そのトランザクション全体が実行されなかったことになります。これはバグではなく、意図的な仕様です。レコードの半分だけ追加される、というような中途半端な状態を防いでいます。原因は接続が切れたことかもしれませんし、SQL文自体に誤りがあるのかもしれませんが、理由が何であれ「全部完了して初めて記録される」というのが原則です。

一貫性（Consistency）があるからこそ、トランザクションが完了したとみなされる前に、変更が確実に反映されます。銀行取引のような場面では、この一貫性が何より重要です。

独立性（Isolation）は、複数のトランザクションが同時に走っても互いに影響し合わないことを意味します。例えば、あなたと友人が同じデータベースの同じレコードに同時にアクセスしていて、あなたがそのレコードを削除するトランザクションを実行し、友人がそのレコードを検索するトランザクションを実行したとします。どちらが先に完了するかによって結果が決まり、中途半端に両方の結果が混ざることはありません。これにより、同時アクセスによる競合を抑えられます。

永続性（Durability）は、コミット（確定）されたトランザクションは失われないという性質です。一度トランザクションが完了し、データベースに反映されると、そのデータは確定したものとして扱われます。中途半端な状態のまま保存されることはありません。

📌 ACIDのおかげでRDBMSは「壊れにくい」システムになっています。壊すこと自体は不可能ではありませんが、他の多くの仕組みに比べて、格段に壊れにくく設計されています。
🍎 かんたん説明

ACID＝「全部成功か全部失敗（原子性）」「変更は確実に反映（一貫性）」「他の処理に邪魔されない（独立性）」「確定したら消えない（永続性）」。この4つがRDBMSの信頼性の源です。

💻 ミニ練習：CHECK制約で一貫性を守る

instructor_id（整数・主キー）とsalary（数値）を持つinstructorテーブルを作ってください。salaryが0以上でなければならない、というルールをCHECK制約で追加し、矛盾したデータが入らないようにしましょう（＝一貫性／Consistency）。

CREATE TABLE instructor (
    instructor_id integer PRIMARY KEY,
    salary numeric CHECK (salary >= 0)
);

CHECK制約があると、条件を満たさないINSERT/UPDATEはデータベース側で自動的に拒否されます。これも「一貫性」を保つ仕組みの1つです。

④

RDBMSのメリット

今でも現役で使われ続けている理由

「MongoDBのようなNoSQLも聞くけれど、SQLを学ぶ価値はまだあるの？」——答えは間違いなくYesです。多くの大手企業が今もRDBMSを使い続けています。例えば、学校の校務情報システムの大部分は、裏側で何らかのリレーショナルデータベースを動かしています。それだけで全米に何百万人もの利用者がいる規模であり、世界規模ではさらに膨大です。企業・自治体（裁判所の記録、警察の交通記録など）・サーバー環境（Windowsサーバーなど）——リレーショナルデータベースはあらゆる場所で使われています。

RDBMSの主なメリットをまとめると、次の通りです。

メリット内容
効率的なデータアクセス比較的シンプルなコマンドで、大量のデータから必要な情報だけを的確に取り出せる
データの整合性とセキュリティACIDによる永続性（persistency）が、データが正しく記録されることを保証する
管理のしやすさデータの整理・クリーニング・監視といった管理作業が、他のシステムに比べて単純
同時アクセスと障害復旧複数ユーザーが同時にアクセスでき、衝突や障害が起きてもバックアップから復旧できるため、データが失われたり壊れたりしにくい
アプリ開発期間の短縮SQLのような対話的な言語で扱えるため、アプリケーション側の開発コストを下げられる
📌 ベンダーによってSQLの「方言」は異なります。就職先や関わる業界によって、使われているRDBMSの種類は変わってきます。「どの現場でどのSQLが使われているか」を調べ、違いを理解しておくことも実務では大切です。
🍎 かんたん説明

RDBMSが今も使われ続けているのは、データを速く正確に取り出せて、管理がしやすく、同時アクセスにも障害にも強く、開発も楽になるから。学校の校務システムも銀行も、裏側の多くはRDBMSです。

💻 ミニ練習：効率的なデータアクセスを体感する

studentテーブルから、tot_credが90より多い学生の名前だけを出力するSQLを書いてください。大量の行から必要な情報だけを素早く取り出せるのが、RDBMSの強みの1つです。

SELECT name FROM student WHERE tot_cred > 90;

数百万行あっても、WHERE句1つで条件に合う行だけに絞り込めます。

⑤

NoSQLとの比較

「NoSQL」は "not SQL" ではなく "not only SQL"

RDBMS以外のモデルとしてよく話題に上がるのがNoSQLです。NoSQLの大きな特徴はスキーマレス（schema-less）であること。まず「スキーマ（schema）」とは何かを確認しましょう。リレーショナルデータベースを設計するとき、私たちは「どんなデータを、どういう単位（テーブル）に分け、それぞれをどう関連づけるか」を事前に定義します。この設計図がスキーマです。例えばUniversityデータベースなら、学生・教員・講座・学校（建物）といった要素をどうテーブルに落とし込むか、という設計がスキーマにあたります。

リレーショナルモデルでは、テーブルを定義する際に列名とデータ型をあらかじめ決め、それを厳密に守らなければなりません（違う型のデータを入れようとするとエラーになります）。NoSQLはこの縛りがなく、事前に構造を固定しません。先生の例えを借りれば、SQLが「型に厳格なJava」だとすれば、NoSQLは「後から柔軟に決められるPython」に近い発想です。

観点RDBMS（SQL）NoSQL
構造スキーマを事前に定義し、厳密に従うスキーマレス。柔軟で構造が固定されない
分散のしやすさ基本的に1台のサーバーが中心。地理的に複製はできるが、容量はそのサーバーの物理的な限界に縛られる複数サーバー・複数の地理的拠点に分散しやすい。クラウドベースで運用されることが多い
得意なデータ規模構造化された、整理されたデータ「データレイク」のような大規模・多様なデータの蓄積
代表的な型テーブル（行と列）キー・バリュー型、グラフ型、ドキュメント型 など

NoSQLの中でもよく見かけるのがドキュメント型です。例えば、あるハッシュキーに、その人（や対象）に関するあらゆる情報をまとめたJSON形式のドキュメントが紐づいている、という形式です。キーさえ分かれば、そのドキュメントを丸ごと取得できます。キー・バリュー型も同様に、あるキーに1つの値を対応させるシンプルな構造で、暗号分野などでも活用されます。

📌 「NoSQL」は "not SQL"（SQLを使わない）という意味ではなく、"not only SQL"（SQLだけではない）の略です。SQLとNoSQLは対立するものではなく、多くの企業はアプリケーションの用途や機能ごとに両方を使い分けています。どちらが「勝つ」かという話ではありません。
🍎 かんたん説明

NoSQLはスキーマを事前に固定しない分、分散させやすく大規模データに向いています。RDBMSは構造が厳格な分、整合性と管理のしやすさに優れます。「NoSQL＝SQL不要」ではなく「SQLだけではない」という意味です。

💻 ミニ練習：固定されたスキーマを体感する

studentテーブルの全列を出力するSQLを書いてください。RDBMSでは列（スキーマ）が事前に固定されているので、どんな行でも同じ列構成で返ってきます——これがNoSQLとの大きな違いです。

SELECT * FROM student;

どの行も同じ列（student_id, name, dept_name, tot_cred...）を持っています。NoSQLのドキュメント型なら、行ごとに持っている項目が違っても構いません。
