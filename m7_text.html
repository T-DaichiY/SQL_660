🔤 M7+：文字列関数・正規表現・全文検索

M7の講義では、REPLACEやSUBSTRINGなどの基本的な関数でデータを整えました。この1本は講義では扱っていない、教科書『Practical SQL 完全ガイド』第14章（テキストマイニング）の内容です。文字列関数を一通り整理し、正規表現でパターン検索・置換を行い、最後にPostgreSQLの全文検索（tsvector / tsquery）の考え方まで学びます。例題はすべて練習用テーブルds_jobs（30行）の実データで、出力はこの教材のエンジンで実際に確認した値です。

①

文字列関数ツールキット

upper・lower・initcap・char_length・trim・lpad と、LIKE / ILIKE の違い

データ整形で一番よく使うのは、やはり文字列の関数です。PostgreSQLには50以上の文字列関数がありますが、実務で毎日のように使うのは十数個。講義ではleft()・right()・replace()・||（連結）を使いました。ここではそれらを復習しながら、講義に出てこなかった関数（大文字小文字の変換、文字数、trimの応用、lpad）を加えて、ひとつの表にまとめます。

📚 データについて：この教材の練習用データ（30行）は、講義で使ったKaggle／Glassdoorの実データ（Uncleaned_DS_jobs.csv、672行）から抜き出した30行のサンプルです。会社名や求人は本物なので、表記ゆれや-1などの汚れもそのまま残っています。なお教科書の例題はus_counties_pop_est_2019（郡の人口）・crime_reports（犯罪報告書）・president_speeches（大統領演説）というテーブルを使っています。このページでは同じ考え方をds_jobsのjob_title・company・job_desc・locに置き換えて説明します。

表の結果はすべてこの教材のエンジンで実行して確認したものです。では実データでupper()・char_length()・trim(x, 'chars')を使ってみましょう。post_idが0と93の行は、「表記ゆれのある職種名」の例です（0番はSr Data Scientist、93番は括弧や末尾の-が付いています）。

SELECT post_id, job_title,
       UPPER(job_title) AS title_upper,
       CHAR_LENGTH(job_title) AS len,
       TRIM(job_title, ' -') AS title_trim
FROM ds_jobs
WHERE post_id IN (0, 93);
post_id | job_title | title_upper | len | title_trim 0 | Sr Data Scientist | SR DATA SCIENTIST | 17 | Sr Data Scientist 93 | (Sr.) Data Scientist - | (SR.) DATA SCIENTIST - | 22 | (Sr.) Data Scientist
📌 trim(x, 'chars')は「文字の集合」を取る：第2引数は' -'（空白とハイフン）の並びではなく、どれか1文字でも当てはまれば削る文字の集合です。前後から、集合に含まれない文字にぶつかるまで削り続けます。そのため93番の末尾の' -'だけが消え、先頭の(Sr.)の括弧や途中の空白は残ります（括弧も消したいなら、集合を' -()'にします）。ltrim・rtrimで片側だけ削ることもできます。

initcap()の落とし穴：略語を認識しない

initcap()は便利ですが「単語の先頭以外を全部小文字にする」だけの単純な関数で、略語（ETL・SQL・AIなど）を理解しません。industry列の411番（業種名IT Services）でその弱点を確認します。

SELECT industry,
       INITCAP(industry) AS titled
FROM ds_jobs
WHERE post_id = 411;
industry | titled IT Services | It Services
⚠️ ITがItになってしまいました。教科書の例でもinitcap('Practical SQL')はPractical Sqlになります。'AI research at NASA'もAi Research At Nasaです。完璧なタイトルケース変換ではないので、略語を含む列では結果を必ず目で確認し、必要ならreplace()で直しましょう（例：replace(initcap(industry), 'It ', 'IT ')）。

LIKE と ILIKE（大文字小文字の扱い）

M3で学んだLIKEは、PostgreSQLでは大文字小文字を区別します。区別しない検索にはILIKE（Insensitive LIKE）を使います。たとえばjob_title LIKE 'senior%'は、PostgreSQLではSenior Data Scientistにマッチしません（先頭がSと大文字のため）。ILIKE 'senior%'ならマッチします。

SELECT COUNT(*) FROM ds_jobs
WHERE job_title ILIKE 'senior%';
count 5
💡 PostgreSQLのILIKEは、この演習アリーナでも自動変換されてそのまま動きます。ただしSQLite（アリーナのエンジン）のLIKEは元から大文字小文字を区別しないので、アリーナではLIKE 'senior%'も同じ5行になります。本物のPostgreSQLでLIKEを使うときは、この違いに注意してください。
🍎 かんたん説明

文字列関数は「文字を整える道具箱」です。大文字小文字をそろえる（upper/lower）、余分な空白や記号を削る（trim）、長さを測る（char_length）、桁をそろえる（lpad）。initcapは便利ですが、略語には弱いので目視チェックを忘れずに。

💻 ミニ練習：職種名を大文字にして文字数も見る

ds_jobsから、post_idが0と93の行について、post_id・UPPER(job_title)（別名title_upper）・CHAR_LENGTH(job_title)（別名len）を求めるSQLを書いてください。

SELECT post_id,
       UPPER(job_title) AS title_upper,
       CHAR_LENGTH(job_title) AS len
FROM ds_jobs
WHERE post_id IN (0, 93);

UPPER()で大文字化、CHAR_LENGTH()で文字数を返します。結果は2行で、lenは17と22になるはずです（空白や末尾の-も文字数に含まれます）。

②

正規表現でテキストを検索・置換する

~ ~* !~ !~* ／ regexp_replace ／ SUBSTRING(x FROM 'pattern')

正規表現（regular expression、regex）は、「数字が1〜2桁」「Srまたはsenior」のように文字列のパターンを書く記法です。LIKEの%と_だけでは書けない複雑な条件を、1行で表せます。最初はとっつきにくいですが、多くのプログラミング言語・エディタで共通して使えるので、覚えて損はありません。

記法意味例
.改行以外の任意の1文字s.r は sir, s1r ...
[a-z]a〜zの範囲の1文字（[0-9]は数字1文字）[A-Z]{2} は CA, WA ...
\d / \w / \s数字／英数字と_／空白\d\d は 2桁の数字
? / * / +直前が0〜1回／0回以上／1回以上sr\.? は sr と sr.
{m} / {m,n}直前をちょうどm回／m〜n回\d{1,3} は 1〜3桁
a|baまたはbanalyst|engineer
( )グループ化（抽出する部分の指定にも使う）^(Sr|Senior)
^ / $文字列の先頭／末尾[0-9]\.[0-9]$ は末尾の 3.1 など
💡 .や?などの記号そのものを探したいときは、直前に\を付けます（\.はピリオド1文字）。パターンを作るときは、regexr.comなどのオンラインツールに文字列を貼って試しながら組み立てると、理解がずっと早くなります。

WHERE で使う照合演算子 ~ ~* !~ !~*

演算子意味
~正規表現にマッチする（大文字小文字を区別する）
~*マッチする（大文字小文字を区別しない）
!~マッチしない（区別する）
!~*マッチしない（区別しない）

講義では、職種名の表記ゆれ（Sr・Sr.・(Sr.)・Senior...）をREPLACEで何回かに分けて直しました。正規表現なら「シニア系の職種」を1つのパターンで拾えます。

SELECT post_id, job_title
FROM ds_jobs
WHERE job_title ~* 'sr\.?|senior'
ORDER BY post_id;
post_id | job_title 0 | Sr Data Scientist 93 | (Sr.) Data Scientist - 98 | Senior Data Scientist 131 | Senior Data Engineer 142 | Senior Data Scientist 155 | Sr Data Scientist 169 | Sr Data Analyst 207 | Senior Business Intelligence Analyst 377 | Sr. Data Scientist 551 | Senior Data Scientist (10 rows)

10行ヒットしました。Sr・Sr.・(Sr.)・Seniorという表記ゆれが、1つのパターンで全部拾えています。同じ条件で演算子を変えると、次のように件数が変わります（すべて実測）。

条件件数ポイント
job_title ~ 'senior'0小文字のseniorはどこにもない（区別する）
job_title ~* 'senior'5Senior始まりの5行（Sr系は含まない）
job_title ~* 'sr\.?|senior'10Sr系とSenior系の両方
job_title !~* 'sr\.?|senior'20それ以外（10 + 20 = 全30行）
job_title ~ '^(Sr|Senior)'9^で「先頭が」を指定。(Sr.) ...（93番）は先頭が括弧なので取りこぼす
job_title ~* 'analyst|engineer'11Analyst系 5行（Data Analyst 3 + Sr Data Analyst 1 + Senior Business Intelligence Analyst 1）＋ Engineer系 6行（Data Engineer 2 + Senior Data Engineer 1 + Machine Learning Engineer 3）
💡 PostgreSQLの~・~*・!~・!~*は、この演習アリーナでも自動変換されてそのまま動きます（アリーナの正規表現はJavaScript風の書き方ですが、このページのパターンならどちらでも同じ動作です）。

regexp_replace()：パターンで置換する

regexp_replace(文字列, パターン, 置換後 [, フラグ])は、replace()の正規表現版です。フラグに'g'（global）を付けるとマッチしたすべてを置換し、付けないと最初の1か所だけ置換します。'i'で大文字小文字を無視できます。

SELECT REGEXP_REPLACE('aaa', 'a', 'b')        AS first_only,
       REGEXP_REPLACE('aaa', 'a', 'b', 'g')   AS all_matches,
       REGEXP_REPLACE('a  b   c', '\s+', ' ', 'g') AS squeezed;
first_only | all_matches | squeezed baa | bbb | a b c

本番は講義で最も面倒だった「会社名の末尾にくっついた評価値」です。実データのcompanyは、Healthfirst＋改行＋3.1のように、会社名の後ろに改行（CHAR(10)）と評価値が付いています（ratingが-1の行は付いていません）。講義ではSUBSTRING(company FROM 1 FOR LENGTH(company) - 4)のように末尾4文字（改行1文字＋3.1の3文字）を削り、評価が-1の行はCASEで除外しました。正規表現なら「末尾の改行 数字.数字」を空文字に置き換えるだけです（改行は\nと書きます）。

SELECT post_id, company,
       REGEXP_REPLACE(company, '\n[0-9]\.[0-9]$', '') AS clean
FROM ds_jobs
WHERE post_id IN (0, 98, 158, 411);
post_id | company | clean 0 | Healthfirst\n3.1 | Healthfirst 98 | GutCheck\n3.8 | GutCheck 158 | Radical Convergence | Radical Convergence 411 | Evolvinc | Evolvinc

※ 出力の\nは、その位置に改行文字が入っていることを示す表記です。

📌 SUBSTRING／LEFT方式との違い：末尾4文字を削る方法は、評価が付いていない行（rating = -1の4行）まで削ってしまい、Radical ConvergenceがRadical Convergになります。だからCASEが必要でした。regexp_replaceは「パターンにマッチしたときだけ置換」するので、評価が付いていない行は自動的にそのままです。実際、パターンにマッチするのは26行で、これは評価が-1でない行の数（30 - 4）と一致します。改行（\n）を含めずに'[0-9]\.[0-9]$'だけで置換すると、Healthfirstの後ろに改行が残るので注意しましょう。
⚠️ 正規表現は強力なぶん、思わぬ行にもマッチする危険があります。UPDATEの前には必ずSELECTで置換結果を確認しましょう（講義で学んだ「バックアップ」「WHEREなしのUPDATEは全行に効く」も同じです）。

もう1つ、salary_est末尾の(Glassdoor est.)と(Employer est.)も、括弧の中身が2種類あっても1つのパターンで消せます。ただし実データには$145K-$225K(Employer est.)のように括弧の前に空白がない行（313番と317番）があるので、空白は?で「あってもなくてもよい」にします。

SELECT post_id, salary_est,
       REGEXP_REPLACE(salary_est, ' ?\(.*\)$', '') AS salary_only
FROM ds_jobs
WHERE post_id IN (0, 313);
post_id | salary_est | salary_only 0 | $137K-$171K (Glassdoor est.) | $137K-$171K 313 | $145K-$225K(Employer est.) | $145K-$225K

\(と\)は「括弧そのもの」、.*は「何でも0文字以上」の意味です。もし空白なしの' \(.*\)$'で書くと、313番は変更されずに残ってしまいます。

SUBSTRING(x FROM 'pattern')：最初のマッチを取り出す

講義のSUBSTRING(x FROM 位置 FOR 長さ)は位置で切り出しました。FROMの後ろに正規表現を書くと、パターンにマッチした最初の部分を取り出せます。パターンに括弧( )があると、その中身だけが返ります。給与の数字を取り出すのに便利です。教科書にも「テキストから4桁の数字を取り出す」という例があります。

SELECT post_id, salary_est,
       SUBSTRING(salary_est FROM '[0-9]+')       AS low_k,
       SUBSTRING(salary_est FROM '-\$([0-9]+)K') AS high_k
FROM ds_jobs
WHERE post_id IN (75, 313, 510);
post_id | salary_est | low_k | high_k 75 | $79K-$131K (Glassdoor est.) | 79 | 131 313 | $145K-$225K(Employer est.) | 145 | 225 510 | $212K-$331K (Glassdoor est.) | 212 | 331

[0-9]+は「数字の連続」で、文字列中の最初の連続（下限）が取れます。-\$([0-9]+)Kは、ハイフンと$の後ろの数字だけを括弧で切り出しています。下限が2桁（79）でも3桁（145や212）でも同じパターンで取れる点が、位置を数える方法との大きな違いです。取れたものは文字列なので、数値として使うときは::intで変換します。

PostgreSQL専用の抽出関数（教科書のみ）

教科書では、犯罪報告書crime_reportsの自由記述文から日付を取り出すために、次の関数を使います。

  • regexp_match(text, pattern)：最初のマッチを配列で返す。教科書ではregexp_match(original_text, '\d{1,2}\/\d{1,2}\/\d{2}')で最初の日付（M/D/YY）を取り出し、(...)[1]::dateで日付型にしてUPDATEで列に入れています。
  • regexp_matches(text, pattern, 'g')：'g'を付けるとすべてのマッチを1件ずつ行として返す（1つの報告書に日付が2つ出てくる場合など）。
  • regexp_split_to_table(text, pattern)：パターンで文字列を分割し、1要素1行のテーブルにする。

この教材のデータに当てはめると、たとえばregexp_match(salary_est, '\$(\d+)K-\$(\d+)K')は0番の行で配列{137,171}を返し、[1]が下限・[2]が上限です。competitorsをregexp_split_to_table(competitors, ',\s*')で分割すれば、0番のEmblemHealth, UnitedHealth Group, Aetnaが3行になります（なおcompetitorsの大半は-1で、これも後でNULLに直す対象です）。

⚠️ この3つの関数は、このサイトの演習アリーナ（SQLite）では動きません。「読んで理解する」内容です。アリーナで同じことをするときは、この単元のSUBSTRING(x FROM 'pattern')とregexp_replace()を使いましょう（この2つはアリーナでも実行できます）。
🍎 かんたん説明

正規表現は「文字のあみ」です。~はあみにかかる行を探し、regexp_replaceはかかった部分を別の文字に置き換え、SUBSTRING(x FROM 'pattern')はかかった部分だけを取り出します。まずSELECTで何がかかるかを確かめてから、UPDATEに進みましょう。

💻 ミニ練習：会社名の末尾の評価値を消す

ds_jobsのcompanyの末尾にくっついた改行＋評価値（\n3.1のような改行 数字.数字）をREGEXP_REPLACEで取り除き、post_idとclean_name（別名）をpost_id順に返すSQLを書いてください。

SELECT post_id,
       REGEXP_REPLACE(company, '\n[0-9]\.[0-9]$', '') AS clean_name
FROM ds_jobs
ORDER BY post_id;

パターン\n[0-9]\.[0-9]$は「文字列の末尾にある改行・数字・ピリオド・数字」を表し、空文字''に置換しています。30行すべてが返り、評価の付いていない4行（post_id 158, 411, 519, 613）は元の名前のままです。

全文検索（読んで理解する）

tsvector・tsquery・@@・GINインデックス・ts_rank()
⚠️ このサイトの演習アリーナ（SQLite）にはtsvector/tsqueryが無いので、この単元は「読んで理解する」専用です。ここに出てくるSQLは本物のPostgreSQL（自分のPCのpgAdminなど）で動くもので、アリーナでは実行できません。結果として示す値は、PostgreSQLの英語辞書の動作に基づく想定です。

LIKE '%word%'や正規表現でも文字列の検索はできますが、長い文章を「意味に近い形」で検索するには足りません。PostgreSQLには、全文検索（full text search）という専用の仕組みがあります。教科書では79本の大統領演説から特定の話題を探すために使っています。

tsvector：検索用に整えた文章

to_tsvector('english', 文章)は、文章をレキシーム（lexeme：正規化された語）の集合に変換します。処理は3つです。

  1. ストップワード（I, am, the, to, with のような意味の薄い語）を捨てる
  2. 単語を語幹にそろえる（stemming：walking → walk、sitting → sit）
  3. 各語の位置を記録する
SELECT to_tsvector('english',
       'I am walking across the sitting room to sit with you.');
'across':4 'room':7 'sit':6,9 'walk':3

教科書の例です。walkingはwalkに、sittingとsitはどちらもsitにまとまり、位置は6番目と9番目と記録されています。

tsquery と @@ 演算子：検索語を作って照合する

検索語はto_tsquery()でtsquery型にします。&（かつ）・|（または）・!（でない）を組み合わせられ、検索語も同じように語幹化されます。@@演算子でtsvectorとtsqueryを照合すると、真偽値（true / false）が返ります。

SELECT to_tsquery('english', 'walking & sitting');
-- 結果： 'walk' & 'sit'

SELECT to_tsvector('english', 'I am walking across the sitting room')
       @@ to_tsquery('english', 'walking & sitting');
-- 結果： true

SELECT to_tsvector('english', 'I am walking across the sitting room')
       @@ to_tsquery('english', 'walking & !sitting');
-- 結果： false   （sitはあるので「!sit」が満たされない）

なぜ LIKE '%word%' では足りないのか

ds_jobsのjob_descで考えてみます（30行のうち0番の説明文は... defining, building, and improving statistical models ...で始まります）。

比べる点LIKE '%word%'全文検索
語形の違いLIKE '%improve%'は0行（improvingはimproveという文字列を含まない）to_tsquery('english', 'improve')も説明文側のimprovingも語幹improvにそろうので、0番の行にマッチする
大文字小文字PostgreSQLのLIKE '%data%'は小文字のdataを含む4行だけ。ILIKEや~*なら18行（Data Analystなど大文字始まりも含む）自動で小文字化して照合
複数語・論理条件ANDやORを何度も書く必要がある'model & data'のように1つの検索語で書ける
関連度の順位付けられない（あるか無いかだけ）ts_rank()でスコア順に並べられる
速度先頭が%のLIKEは通常のインデックスが効かず全行を走査GINインデックスで高速化できる

上の「モデルとデータを両方含む説明」は、正規表現ならjob_desc ~* 'model' AND job_desc ~* 'data'で2行（post_idの0と78。0番はmodels、78番はModeling）と確認できます。全文検索ならmodelsもModelingも語幹modelにそろいます。全文検索で同じ条件を書くと次のようになります。

SELECT post_id, job_desc
FROM ds_jobs
WHERE to_tsvector('english', job_desc)
      @@ to_tsquery('english', 'model & data');
-- 想定結果： post_id 0 と 78 の2行

tsvector列とGINインデックス

上のように毎回to_tsvector()を呼ぶと、検索のたびに全行を変換するので遅くなります。教科書では、tsvector型の列を別に作って変換結果を保存し、その列にGINインデックスを張ります（GIN = 語から行を引く転置インデックス）。

ALTER TABLE ds_jobs ADD COLUMN search_desc tsvector;

UPDATE ds_jobs
SET search_desc = to_tsvector('english', job_desc);

CREATE INDEX desc_idx ON ds_jobs USING gin(search_desc);

SELECT post_id, job_desc
FROM ds_jobs
WHERE search_desc @@ to_tsquery('english', 'model & data');
💡 アリーナとの違い：この手順のうちALTER TABLE ... ADD COLUMNとUPDATEの形はアリーナでも使える書き方ですが、tsvector型・to_tsvector()・USING ginはSQLiteに存在しないため動きません。

ts_rank()：関連度でランキングする

ts_rank(tsvector, tsquery)は、検索語がどれだけ含まれているかに基づく関連度スコアを返します。ORDER BY score DESCで「一番それらしい」行が上に来ます。教科書では「war & security & threat & enemy」で演説をランキングしています。

SELECT post_id, job_desc,
       ts_rank(search_desc, to_tsquery('english', 'model & data')) AS score
FROM ds_jobs
WHERE search_desc @@ to_tsquery('english', 'model & data')
ORDER BY score DESC;
⚠️ 長い文章ほど有利になりがち：教科書の演説ランキングで1位になったクリントン1997年の演説は、単に演説が長いから上位に来ている面もあります。そこでts_rank()の第3引数（正規化コード）を使います。たとえばts_rank(search_desc, query, 1)とすると、スコアを文書の長さで補正し、長さの違う文書を公平に比べられます。
🍎 かんたん説明

全文検索は「図書館の索引」です。本を丸ごと探す代わりに、本文を語のリストに整理（tsvector）しておき、検索語（tsquery）と突き合わせます。語形の違いも大丈夫で、関連度順に並べることもできます。ただしアリーナでは動かないので、仕組みと書き方を読んで理解しましょう。

📖 読んで理解：全文検索のSQLを書けるか自己チェック

この問題はキーワードだけの自己チェックです。模範解答はPostgreSQL専用のSQLで、このサイトのアリーナでは実行できません。ds_jobsのjob_descから、'model & data'に一致する行を、関連度スコアscoreの高い順に返すSQLを、to_tsvector('english', ...)・to_tsquery・@@・ts_rankを使って書いてみてください。

SELECT post_id, job_desc,
       ts_rank(to_tsvector('english', job_desc),
               to_tsquery('english', 'model & data')) AS score
FROM ds_jobs
WHERE to_tsvector('english', job_desc)
      @@ to_tsquery('english', 'model & data')
ORDER BY score DESC;

WHEREで@@によりtsvectorとtsqueryを照合し、ts_rank()のスコアで並べ替えています。PostgreSQL専用なのでアリーナでは動きません。「答え合わせ」ではキーワードが含まれているかだけを確認します。
