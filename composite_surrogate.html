M5 · Primary keys Part 2

🧩 主キー② — 複合キーと代理キー

1列だけでは一意にならないときは複合キー、意味のある列を使いたくないときは代理キー。それぞれの書き方と弱点を見ていきます。

① 複合キー② 代理キーとIDENTITY③ 代理キーの弱点④ 発展：手動採番📝 Quiz
①

複合キー — 2列以上で一意にする

テーブル制約でしか書けない

前のレッスンで見た主キーは、いつも1列でした。しかし現実のデータでは、1列だけでは一意にならないことがあります。たとえば大学の教室を表すclassroomを考えてみましょう。同じ「105」という部屋番号は、建物が違えば別の部屋として存在してよいはずです。

こういうときは、room_numberとbuildingの2列を組み合わせて初めて一意になる、という主キーを作ります。これが複合キー（composite key）です。

⚠️ 複合キーは列制約では書けません。「この列とこの列を組み合わせて1つの主キーにする」という指定は、必ずテーブル制約としてCONSTRAINT 名 PRIMARY KEY (列1, 列2)の形で書きます。列の後ろにPRIMARY KEYを並べて書いても、それは「別々の主キーが2つある」という意味にはなりません（そもそも主キーはテーブルに1つだけです）。

▶ classroomテーブルを作る

CREATE TABLE classroom (
    room_number varchar(7),
    building varchar(15),
    capacity numeric,
    CONSTRAINT room_key PRIMARY KEY (room_number, building)
);
CREATE TABLE

ここまでは通常のテーブル定義と同じですが、最後の1行だけが特別です。room_numberとbuildingの組み合わせが一意でなければならない、とデータベースに伝えています。

▶ 3件INSERTしてみる

INSERT INTO classroom (room_number, building, capacity)
VALUES ('105', 'Science', 35);
INSERT 0 1
INSERT INTO classroom (room_number, building, capacity)
VALUES ('105', 'Arts', 25);
INSERT 0 1

部屋番号「105」は同じですが、建物がScienceとArtsで違うので、どちらも成功します。組み合わせで見れば別の部屋だからです。では、まったく同じ組み合わせをもう一度入れるとどうなるでしょうか。

INSERT INTO classroom (room_number, building, capacity)
VALUES ('105', 'Science', 45);
ERROR: duplicate key value violates unique constraint "room_key" DETAIL: Key (room_number, building)=(105, Science) already exists.

capacityを45に変えても関係ありません。主キーの列（この場合はroom_numberとbuildingのペア）がすでに存在する組み合わせだったので、拒否されます。

一意性チェックの仕組み（room_number + building）
1️⃣
(105, Science)この組み合わせは初登場 → 挿入OK
↓
2️⃣
(105, Arts)room_numberは同じ105だが、building が違うので別の組み合わせ → 挿入OK
↓
3️⃣
(105, Science) をもう一度まったく同じ組み合わせがすでに存在 → ❌ エラーで拒否
判定されるのは「room_numberだけ」でも「buildingだけ」でもなく、2列のペア。
📌 教科書ではこう：教科書は履修記録の例としてnatural_key_composite_exampleというテーブルを使っています。student_idとschool_day（授業を受けた日）を組み合わせた複合主キーで、「同じ生徒が同じ日に同じ授業を2回受けたことにはならない」という制約を表現しています。考え方はclassroomの例とまったく同じです。
🍎 かんたん説明

複合キーは「この列とこの列を合わせて初めて重複禁止」というルール。書けるのはテーブル制約だけです。

②

代理キー — GENERATED ALWAYS AS IDENTITY

データベースに番号を自動で振らせる

自然キー（免許証番号やメールアドレスのように、現実世界にすでに存在する値）には便利さがある一方、「本当に絶対に重複しないのか」を人間が保証しきれない、という不安が残ります。そこで使われるのが代理キー（surrogate key）——現実世界とは無関係に、データベース自身が発行する連番です。

PostgreSQLではGENERATED ALWAYS AS IDENTITYという句を列に付けることで、その列を自動採番の代理キーにできます。

▶ studentsテーブルを作る

CREATE TABLE students (
    student_id bigint GENERATED ALWAYS AS IDENTITY,
    first_name text,
    last_name text,
    email text,
    CONSTRAINT student_key PRIMARY KEY (student_id)
);
CREATE TABLE
⚠️ データ型はintegerではなくbigintにしましょう。integerが扱える最大値は約21億（2,147,483,647）です。大学の全学生に連番を振るだけなら余裕ですが、注文明細やログのように行数が急増するテーブルでは、この上限に本当にぶつかる事故が起きます。bigintなら約922京（9,223,372,036,854,775,807）まで扱えるので安心です。

INSERTするときは、列名を明示的に指定してstudent_idを省略します。値を書かなければ、データベースが自動で次の番号を割り当ててくれるからです。

▶ 3人まとめてINSERT

INSERT INTO students (first_name, last_name, email)
VALUES
    ('Jim', 'Harbaugh', 'jharbaugh@example.edu'),
    ('Alison', 'Ray', 'aray@example.edu'),
    ('Jacqueline', 'Smith', 'jsmith@example.edu');
INSERT 0 3
SELECT * FROM students;
student_id | first_name | last_name | email -----------+------------+-----------+------------------------ 1 | Jim | Harbaugh | jharbaugh@example.edu 2 | Alison | Ray | aray@example.edu 3 | Jacqueline | Smith | jsmith@example.edu

誰も番号を指定していないのに、1, 2, 3という連番が挿入した順に自動で割り振られました。これが代理キーの基本的な使い方です。

📌 IDENTITYはANSI標準です。古いPostgreSQLのコードではserialやbigserialという型で同じことを実現していましたが、これらはPostgreSQL独自の仕組みでした。GENERATED ALWAYS AS IDENTITYはSQL標準（ANSI SQL）に沿った書き方なので、今後はこちらを使うのが推奨されます。
🍎 かんたん説明

代理キーは「意味のない連番」。GENERATED ALWAYS AS IDENTITYを付ければ、INSERT時に番号を省くだけで自動採番されます。

③

代理キーの弱点

「意味がない」ことは長所でもあり短所でもある

代理キーには大きな弱点があります。student_idは自動で採番されるだけなので、同じ人物を何度INSERTしても、データベースは何も気づいてくれません。

▶ 同じ人をもう一度入れてしまう

INSERT INTO students (first_name, last_name, email)
VALUES ('Jim', 'Harbaugh', 'jharbaugh@example.edu');
INSERT 0 1 （student_id = 4 として、まったく同じ人物がもう1行できてしまう）

複合キーや自然キーと違い、代理キー自体は「これは重複か？」を判断する材料を何も持っていません。student_idは常に新しい値になるので、主キー制約はいつでも満足されてしまうのです。

⚠️ 対策：意味のある列にUNIQUEを追加する。たとえばemail列にUNIQUE制約を付けておけば、同じメールアドレスでの二重登録は防げます。主キー（代理キー）で「行の一意な識別」を、UNIQUE制約（自然キーに近い列）で「現実世界での重複防止」を、それぞれ別の役割として持たせるのが実務的な解決策です。UNIQUE制約の詳しい使い方は次のレッスン「制約」で扱います。
🪪
自然キー
driver_id, email
現実世界に意味がある値
🔢
代理キー
student_id (IDENTITY)
DBが発行するだけの連番
🧩
複合キー
room_number + building
組み合わせで一意

自然キー vs 代理キー

長所短所
自然キー追加の列が要らない／現実の意味を持つので、他の情報と結び付けて考えやすくJOINが減ることもある「絶対に重複しない」という前提が後から崩れることがある（免許証番号が州をまたいで重複するなど）
代理キーデータの内容に左右されず、常に一意であることが保証される余分な列が1つ増える／その値自体には現実世界の意味が無い
🍎 かんたん説明

代理キーは重複を防いでくれません。「同じ人を2回登録しない」ようにするには、別途UNIQUE制約が必要です。

④

発展：番号を手動で入れる／振り直す

教科書のみで扱う内容

ここは講義では扱われていませんが、教科書に載っている発展的な内容です。GENERATED ALWAYS AS IDENTITYは名前の通り「常に」自動採番するのが基本ですが、どうしても明示的な値を手動で挿入したい場面があります（たとえば他システムからのデータ移行で、元の番号を保持したい場合など）。そのときはOVERRIDING SYSTEM VALUEを使います。

▶ 番号を手で指定してINSERTする

INSERT INTO surrogate_key_example
OVERRIDING SYSTEM VALUE
VALUES (4, 'Chicken Coop', '2021-09-03 10:33-07');
INSERT 0 1

OVERRIDING SYSTEM VALUEを付けることで、「本来は自動採番される列だが、今回だけ自分で指定した値を使う」とデータベースに伝えられます。

⚠️ 注意：内部の連番カウンターはズレたままです。手動で4番を入れても、データベースの自動採番の仕組みは「次は何番か」を独自に覚えているので、続けて自動INSERTすると番号が重複したりおかしな順序になったりすることがあります。そこで、カウンターを追いつかせる（再同期する）必要があります。

▶ 次の自動採番を5番から始めさせる

ALTER TABLE surrogate_key_example
ALTER COLUMN order_number RESTART WITH 5;
ALTER TABLE

RESTART WITHで、次に自動採番される番号を明示的に指定できます。これで手動INSERTした4番と、その後自動で振られる5番以降がぶつからなくなります。

📌 覚えておきたいこと：行を削除しても欠番は埋まりません。たとえばstudent_id = 2の行を削除しても、次に自動採番される番号は4のまま（2が再利用されることはない）です。代理キーの連番は「行の順番」ではなく「発行された回数」を表しているだけなので、歯抜けは普通に起こります。
🍎 かんたん説明

普段は自動採番に任せますが、どうしても手で番号を入れたいときはOVERRIDING SYSTEM VALUE、そのあとカウンターを直すにはRESTART WITHを使います。
