索引という考え方

本の索引＝データベースのインデックス

🎯 これだけ覚えればOK

PRIMARY KEYやUNIQUEを付けると、PostgreSQLが自動でB-tree（既定のインデックス）を作ってくれる。これのおかげで、検索のたびに全行を読まずに済みます。

索引が無い本

1ページ目から順にめくって探す

索引がある本

ページ番号を引いて一発でたどり着く

▶ B-treeが得意な条件（LIKEは先頭が具体的な文字ならOK）

SELECT * FROM new_york_addresses WHERE street = 'BROADWAY';
SELECT * FROM new_york_addresses WHERE street LIKE 'Dorito%';
🍎 ひとことで

先頭にワイルドカードが無いLIKE（'Dorito%'）はOK。先頭が%（'%dorito'）だと索引が使えません。

①

測って比べる：EXPLAIN ANALYZE

389ms → 5ms
⏱️
EXPLAIN ANALYZEを付けると、クエリが実際にかかった時間が分かります。94万行のnew_york_addressesで試すと、インデックス前はExecution Time: 389.232 msでした。

▶ インデックスを作って、もう一度測る

CREATE INDEX street_idx ON new_york_addresses (street);
CREATE INDEX
クエリの条件インデックス前インデックス後
WHERE street = 'BROADWAY'92 ms5 ms
WHERE street = '52 STREET'94 ms1 ms
WHERE street = 'ZWICKY AVENUE'93 ms1 ms未満
🍎 ひとことで

SQL文は同じでも、CREATE INDEXした後は全行を探す代わりに索引を使うので、桁違いに速くなります。

②

使いどころと注意点

全部の列には付けない
付けると良い列理由
外部キー（FK）の列JOINやCASCADE削除が速くなる（自動では付かない）
WHEREでよく使う列検索の恩恵が大きい
⚠️
インデックスはタダではありません。INSERT・UPDATE・DELETEのたびにインデックスも更新するので、容量が増え、書き込みが遅くなります。付ける前にEXPLAIN ANALYZEで効果を確かめましょう。

🤔 答えられるかな？（クリックで答えが開く）

Q1. PostgreSQLの既定のインデックスの種類は？A. B-tree。PRIMARY KEYやUNIQUEを付けると自動で作られる。
Q2. クエリが実際にかかった時間を調べるコマンドは？A. EXPLAIN ANALYZE。
Q3. 全部の列にインデックスを付けない方がいいのはなぜ？A. 容量が増え、書き込み（INSERT/UPDATE/DELETE）のたびに更新コストがかかるから。
