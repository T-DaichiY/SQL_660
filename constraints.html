M5 · Constraints

🛡️ 制約 — NOT NULL・CHECK・UNIQUE・DEFAULT

テーブル設計の最後の砦は列そのものに付けるルールです。値が空でないか、範囲は正しいか、重複していないか、何も入れなくても既定値が入るか——これが今回のテーマです。

① NOT NULL② CHECK③ UNIQUE vs PK④ DEFAULT⑤ 発展：ALTER TABLE📝 Quiz
①

制約の形と NULL / NOT NULL

属性名 データ型 制約、が基本の形

これまでPRIMARY KEYやREFERENCESを見てきましたが、これらはすべて同じ形に従っています。

📌 列の制約は常に属性名 データ型 制約という順番で書きます。データ型のすぐ後ろに、その列に適用したいルールを続けるだけです。
列を守る4つの制約
1️⃣
データ型まず入れられる値の種類そのものを決める（最初の制約）
↓
2️⃣
NOT NULL空を許すか許さないか
↓
3️⃣
CHECK入っている値の範囲・関係が正しいか
↓
4️⃣
UNIQUE他の行と重複していないか
↓
5️⃣
DEFAULT何も指定されなかったときの初期値を用意
データ型の上に、この4つの制約を重ねてテーブルを守っていきます。
🚫
NOT NULL
空を禁止
first_name NOT NULL
✅
CHECK
値の範囲を判定
CHECK (price > 0)
🆔
UNIQUE
重複を禁止（NULLは複数可）
email UNIQUE
🧩
DEFAULT
未入力時の初期値
DEFAULT CURRENT_DATE

まずいちばん基本的なルールがNULL / NOT NULLです。列は特に何も書かなければ、既定でNULLを許可します——つまり「その情報は空でもよい」という意味です。

CREATE TABLE employees (
    employee_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    first_name varchar(50) NOT NULL,
    middle_name varchar(50) NULL,
    last_name varchar(50) NOT NULL
);
CREATE TABLE Query returned successfully.

middle_name varchar(50) NULLのNULLは「省略してもよい」ことをあえて明記しているだけで、書かなくても結果は同じです。ミドルネームは無い人もいるので、これで問題ありません。

一方first_nameやlast_nameにはNOT NULLを付けています。名前が空のまま従業員データが登録されるのは、明らかにおかしいからです。

⚠️ 「値が要らない」と「値が0である」は別物です。たとえば口座残高の列はNOT NULLにすべきです——残高が入力されていない口座はあり得ません。ただし残高そのものは0や、当座貸越でマイナスになることもあります。「NULLを許さない」ことと「0以上にする」ことは、それぞれ別の制約で表現します（0以上にする方法は次のUnitのCHECKです）。

NOTは「否定」を表す一般的なキーワードで、NOT NULL以外の場所にも登場します。たとえばWHERE user_role NOT IN ('Admin', 'Staff')のように、条件をそのまま反転させるのにも使えます。NOT NULLを「特別な1つのキーワード」ではなく「NULLという条件をNOTで否定したもの」と考えると、他の場面にも応用が利きます。

🍎 かんたん説明

列は何も書かなければNULL（空）OK。「これは絶対に空にしたくない」という列にだけNOT NULLを付けます。

②

CHECK — 値の範囲を制限する

domain integrity（許される値の範囲）を守る

NOT NULLは「空かどうか」しか見ませんが、入っている値そのものが妥当かを判定したいこともあります。それがCHECKです。

📌 CHECKは真偽（Boolean）で判定される論理テストです。テストの結果がTRUEになる行だけが受け入れられます。これはdomain integrity（ドメイン整合性）——「その列に入ってよい値の範囲」を守る仕組みです。
CREATE TABLE products (
    product_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_name text NOT NULL,
    quantity numeric CHECK (quantity >= 0),
    price numeric CHECK (price > 0)
);
CREATE TABLE Query returned successfully.

ここでquantityは>= 0（在庫はゼロもあり得る）なのに対し、priceは> 0（等号なし）にしている点に注目してください。在庫が0個は普通ですが、価格がちょうど0だと「タダで配る」ことになってしまいます。境界の値をどちらに含めるかは、その列が現実に何を意味するかで決めます。

実際に違反する行を入れるとエラーになります。

INSERT INTO products (product_name, quantity, price)
VALUES ('Notebook', 10, 0);
ERROR: new row for relation "products" violates check constraint "products_price_check"

CHECKは日付や文字列にも使えます。

order_date date CHECK (order_date <= CURRENT_DATE),
user_role text CHECK (user_role IN ('Admin', 'Staff'))

1つ目は「注文日は今日より未来にはできない」、2つ目は教科書にも出てくる例で「役割はAdminかStaffのどちらかしか許さない」というCHECKです。

複数の列にまたがるCHECK

CHECKは1つの列だけでなく、同じ行の複数の列を同時に見ることもできます。この場合はテーブル制約として、名前を付けて最後にまとめて書きます。

CREATE TABLE graduates (
    student_id bigint PRIMARY KEY,
    credits numeric,
    tuition text,
    CONSTRAINT grad_check CHECK (credits >= 120 AND tuition = 'Paid')
);
CREATE TABLE Query returned successfully.

もう1つ、小売の値引きでよく出てくる例です。

CONSTRAINT sale_check CHECK (sale_price < retail_price)

これは「セール価格は定価より必ず安い」ことを保証します。quantity >= 0のように1列だけを見るCHECKと違い、こちらは2つの列の関係そのものが正しいかを判定しています。

🍎 かんたん説明

CHECKは「本当に入れていい値か」をTRUE/FALSEで判定する見張り番。1列だけでも、複数列の関係でも書けます。

③

UNIQUE と PRIMARY KEY のちがい

「重複禁止」は同じでも、目的が違う

これまでのレッスンでPRIMARY KEYは「一意」かつ「NULL不可」だと学びました。実は重複を禁止するだけなら、UNIQUEという別の制約もあります。両者はよく似ていますが、使いどころは異なります。

観点PRIMARY KEYUNIQUE
重複禁止禁止
NULL不可複数のNULLを許可
値の変更基本的に変更しない前提後から変更してよい
1テーブルにいくつ1つだけいくつでも

この違いが生きてくるのが、SNSのようなアカウントを持つusersテーブルです。

CREATE TABLE users (
    user_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text UNIQUE,
    username text UNIQUE
);
CREATE TABLE Query returned successfully.

TwitterやFacebookのような大手SNSも、内部的には自動採番されたuser_idのような番号でユーザーを管理していると言われています。emailやusernameは人間が変更したくなるもの（結婚で名字が変わる、メールを乗り換える、ハンドルネームを変える）ですが、内部IDだけは絶対に変えないという前提を置けます。だからこそ、PRIMARY KEYは変更されないuser_idに、変わりうるemailとusernameにはUNIQUEを使うのです。

教科書のデモでも、email_uniqueという名前のUNIQUE制約に同じメールアドレスを2回登録しようとすると、次のエラーになります。

INSERT INTO users (email, username)
VALUES ('slee@example.org', 'sleedup');
ERROR: duplicate key value violates unique constraint "email_unique" DETAIL: Key (email)=(slee@example.org) already exists.
⚠️ PRIMARY KEYはテーブルに1つしか作れません。「重複させたくない列」が複数あるなら、そのうち1つだけをPRIMARY KEYにして、残りはUNIQUEにする——これがこのUnitの結論です。
🍎 かんたん説明

PKは「一生変わらない番号」に。emailやusernameのように人が変えたくなる値はUNIQUEで守ります。

④

DEFAULT と制約の組み合わせ

何も指定しなかったときの初期値

DEFAULTは、INSERT時にその列の値を書かなかったときに自動的に使われる値を指定する制約です。

CREATE TABLE staff (
    staff_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    hire_date date DEFAULT CURRENT_DATE,
    salary numeric DEFAULT 50000
);
CREATE TABLE Query returned successfully.

hire_dateを省いてINSERTすれば今日の日付が、salaryを省けば50000が自動的に入ります。DEFAULTに指定する値は、その列のデータ型と一致していなければなりません。

CHECKとDEFAULTの組み合わせ

1つの列に複数の制約を並べて書くこともできます。順番はどちらが先でも構いません——書かれた制約はすべて評価されます。

price numeric CHECK (price > 0) DEFAULT 99

ここでは、価格を省略すると99が自動的に入り、それがCHECK (price > 0)もちゃんと満たしている——という関係になっています。DEFAULTの値そのものがCHECKに違反していないか、必ず確認しましょう。

⚠️ 制約どうしが矛盾すると、そもそもテーブルが作れなかったり、INSERTが常に失敗したりします。典型的な悪い組み合わせは2つあります。
①同じ列にCHECK (price > 100)とCHECK (price < 50)のように、両立しないCHECKを2つ付けてしまう。
②UNIQUEの列にDEFAULTを付ける。値を省略するたびに同じ既定値が入ろうとするため、2行目のINSERTからUNIQUE違反で失敗します。

逆に、CHECKとDEFAULTの組み合わせ自体はとても相性が良く、実務でもよく使われます。「省略時はこの値、ただし範囲はこの中」という意図がそのままテーブル定義に表現できるからです。

🍎 かんたん説明

DEFAULTは「書かなかったときの初期値」。CHECKとは相性が良いですが、UNIQUEとDEFAULTの組み合わせは危険です。

⑤

発展：既存のテーブルに制約を付け外しする

教科書のみの内容 — ALTER TABLE

ここまでの制約はすべてCREATE TABLEの時点で書いていました。しかし実務では、すでに運用中のテーブルに後から制約を追加したり、逆に外したりする必要が出てきます。これは講義では扱われませんでしたが、教科書に登場する内容です。

-- 既存の制約を一度外して、あらためてPRIMARY KEYとして付け直す
ALTER TABLE not_null_example
DROP CONSTRAINT student_id_key;

ALTER TABLE not_null_example
ADD CONSTRAINT student_id_key PRIMARY KEY (student_id);
ALTER TABLE ALTER TABLE

列単位でNOT NULLを外したり、あとから付け足したりすることもできます。

ALTER TABLE not_null_example
ALTER COLUMN first_name DROP NOT NULL;

ALTER TABLE not_null_example
ALTER COLUMN first_name SET NOT NULL;
ALTER TABLE ALTER TABLE
⚠️ 制約は「既存のデータがそれを満たしているとき」しか追加できません。たとえばfirst_nameにすでにNULLの行が1件でもあれば、SET NOT NULLはエラーになります。同様に、すでに重複した値やNULLが入っている列を、後からPRIMARY KEYにすることはできません。制約を追加する前に、まずデータそのものをクリーンにしておく必要があります。
📌 この発展Unitのポイント——制約は「テーブルを作るときにしか決められないもの」ではなく、あとからALTER TABLEで調整できる、テーブルの成長に合わせて育てていくものです。
🍎 かんたん説明

ALTER TABLEで制約はあとから足したり外したりできます。ただし今あるデータがルール違反だと、追加はできません。

📖 用語集

NOT NULL
非NULL制約
その列を空にすることを禁止する制約。既定ではNULLは許可される。
CHECK
値の範囲制約
TRUE/FALSEで判定する論理テスト。1列でも複数列の関係でも書ける。
domain integrity
ドメイン整合性
列に入ってよい値の範囲が守られている状態。CHECKが担う役割。
UNIQUE
一意制約
重複を禁止するが、NULLは複数許可し、値の変更も想定した制約。
DEFAULT
既定値
値が指定されなかったときに自動的に入る値。
ALTER TABLE
テーブル変更
既存のテーブルに制約を追加・削除するための文。既存データが新しい制約を満たしている必要がある。

💡 学習のヒント

「空にできない？」→NOT NULL。「値の範囲がおかしくない？」→CHECK。「重複だけ防ぎたい、でも変わってもいい？」→UNIQUE。「何も書かなかったらどうなる？」→DEFAULT。この4つの質問で使い分けを判断できます。
