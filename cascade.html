M5 · On Delete Cascade

🌊 ON DELETE CASCADE — 親を消すと子も消える

外部キーがあるだけでは、参照されている親の行は削除できません。「親が消えたら子も自動で消す」を指定するのがON DELETE CASCADEです。

① なぜ必要か・前提② 構文③ 実演📝 Quiz
①

なぜ必要か・使うための前提

外部キーだけでは親を消せない

前のレッスンで、takes.student_idはstudents.student_idをREFERENCESする外部キーだと学びました。この参照関係があるおかげで、存在しない学生の履修は登録できません。

ところが、この参照関係は逆方向にも効いてしまいます。takesにまだstudent_id = 4の行が残っている状態で、studentsから学生4を削除しようとするとどうなるでしょうか。

-- takes にまだ student_id = 4 の履修記録が残っている状態で…
DELETE FROM students WHERE student_id = 4;
ERROR: update or delete on table "students" violates foreign key constraint "takes_student_id_fkey" on table "takes" DETAIL: Key (student_id)=(4) is still referenced from table "takes".
⚠️ 外部キー制約は、参照されている親の行を守ります。そのままでは、まずtakesからstudent_id = 4の行を手作業で全部先に削除してから、ようやくstudents側を削除できます。テーブルが増えるほど、この手順は面倒になり、消し忘れの原因にもなります。

ON DELETE CASCADEを使うと、「親を消したら、それを参照している子も自動的に消す」とデータベースに指示できます。ただし、使うには3つの前提が順番にそろっている必要があります。

CASCADEを使うための3つの前提
1️⃣
主キーがある親テーブル（students）にPRIMARY KEYが定義されている
↓
2️⃣
PK–FK 関係が既にあるREFERENCESで親子関係がすでに成立している
↓
3️⃣
FK側に書くCASCADEは親の主キー側ではなく、子の外部キー側に書く
この3つがそろって初めて、CASCADEが機能する。
📌 なぜ主キー側ではなく外部キー側に書くのか——それは「テーブルごとに挙動を選べるようにするため」です。同じstudentsを参照していても、テーブルによって望ましい削除の挙動は違います。

テーブルごとに選べる削除の挙動（例）

子テーブル学生が退学したら理由
takes（履修・成績記録）残す（CASCADEしない）単位・成績は記録として保持する必要があるため（コンプライアンス上の理由）。
advisor（指導教員の割り当て）CASCADEで消す在籍していない学生への指導関係は、もはや意味を持たないため。
🍎 かんたん説明

外部キーだけでは親を消せません。「消したら子も消す」を選んだテーブルにだけON DELETE CASCADEを付けます。

②

構文

外部キーの定義の末尾に付け足す

ON DELETE CASCADEは、外部キー列の定義の一番最後に書き足すだけです。

student_id bigint REFERENCES students (student_id) ON DELETE CASCADE,

ここで注意が必要です。takesは前のレッスンですでに作ってあるテーブルなので、この1行を今すぐ書き足すことはできません。列の定義を後から変更するには本来ALTER TABLEを使いますが、それはこのモジュールの後半で扱う内容です。

-- ❌ 既存の列定義はこう書き換えられない（ALTER TABLE が必要）
student_id bigint REFERENCES students (student_id) ON DELETE CASCADE; -- 構文として単独では成立しない
⚠️ 今回のレッスンでは、近道としてDROP TABLEでtakesを一度消し、CASCADE付きで作り直します。この方法はtakesの中身（既存データ）を全部消してしまうので、実際の本番環境ではまず使いません。あくまで「今は空のテーブルだから」できる、学習用の近道です。
📌 CASCADEを付けるメリットは、外部キーそのものと同じ方向にあります。孤児レコード（親を失った子の行）が残らないので、後々のクエリでゴミデータに足を取られることがなくなり、データがきれいな状態に保たれます。
🍎 かんたん説明

書く場所は外部キーの定義の末尾。すでにあるテーブルを直すにはALTER TABLEが要りますが、今回は作り直して済ませます。

③

実演：親を消すと子も消える

DROP → CREATE → INSERT → DELETE → SELECT

まずtakesを消し、ON DELETE CASCADE付きで作り直します。

DROP TABLE takes;
DROP TABLE
CREATE TABLE takes (
    student_id bigint REFERENCES students (student_id) ON DELETE CASCADE,
    grade varchar(1)
);
CREATE TABLE

4件の履修記録を入れます。

INSERT INTO takes (student_id, grade)
VALUES
    (1, 'A'),
    (2, 'B'),
    (3, 'C'),
    (4, 'B');
INSERT 0 4

ここで、学生4（student_id = 4）をstudentsから削除します。

DELETE FROM students WHERE student_id = 4;
DELETE 1

今度はエラーになりません。takesの中身を確認してみましょう。

SELECT * FROM takes;
student_id | grade -----------+------- 1 | A 2 | B 3 | C （student_id = 4 の行は消えている）
CASCADEが起きる流れ
1️⃣
親テーブルの行を削除DELETE FROM students WHERE student_id = 4;
↓
2️⃣
データベースが参照している子テーブルを自動で探すON DELETE CASCADEが付いた外部キーをすべてチェック
↓
3️⃣
一致する子の行も削除takesのstudent_id = 4の行が自動で消える
手作業で子テーブルを探して削除する必要はもうない。
📌 削除は1回のコマンドで済み、しかも整合性が崩れません。takesにはstudentsに存在しない学生の行は、もう決して残らなくなります。
🍎 かんたん説明

親を消すだけで、CASCADEが付いた子の行はデータベースが勝手に一緒に消してくれます。

📖 用語集

ON DELETE CASCADE
連鎖削除
外部キー列に付ける指定。親の行が消えたとき、それを参照する子の行も自動的に削除する。
親子テーブル
parent–child table
主キー側（親）と外部キー側（子）の関係にある2つのテーブル。students が親、takes が子。
孤児レコード
orphan record
参照しているはずの親の行が存在しない、宙に浮いた子の行。CASCADEはこれを防ぐ。
DROP TABLE
テーブル削除
テーブルごと（中身も定義も）完全に削除するコマンド。作り直す前に使う。
ALTER TABLE
テーブル変更
既存テーブルの列や制約を後から追加・変更するコマンド。詳しくは制約のレッスンで扱う。
