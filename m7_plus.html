①

重複と表記ゆれを探す

GROUP BY ... HAVING count(*) > 1 で「データのインタビュー」

データを直す前に、まず「何がおかしいのか」を調べるのが鉄則です。教科書10章ではこれを「データのインタビュー」と呼び、最初の道具としてGROUP BY ... HAVING count(*) > 1を使います。M4で学んだGROUP BYとHAVINGの応用です。

📖 教科書の題材について：教科書（Listing 10-2〜10-5）は米国の食肉・食鳥・卵処理施設のテーブルmeat_poultry_egg_establishments（6,287行）を使っています。このページでは同じ考え方を、練習用のds_jobs（30行）に当てはめて説明します。この教材の練習用データ（30行）は講義で使ったKaggleのデータを模した架空のサンプルです。

重複レコードを探す（複数列でGROUP BY）

「同じ会社・同じ場所」の行が2回以上入っていないかを調べます。重複の定義に使う列を全部GROUP BYに並べ、HAVING count(*) > 1で「2行以上あるグループ」だけを残します。

SELECT company_name, location, count(*) AS n
FROM ds_jobs
GROUP BY company_name, location
HAVING count(*) > 1;
(0 rows)
📌 「0行」は立派な結果です。エラーではなく「company_name＋locationの組で重複は1つもない」という確認ができたことを意味します。検査クエリは、問題が見つからなければ0行で返る、と覚えましょう。

表記ゆれを探す（1列でGROUP BY）

同じものが違う綴りで入っていないかは、その列だけでGROUP BYして件数を数え、目で見ます。教科書のListing 10-5では会社名Armour-Eckrich Meatsが4通りの綴りに分かれていました。ds_jobsではjob_titleが該当します。

SELECT job_title, count(*) AS n
FROM ds_jobs
GROUP BY job_title
ORDER BY job_title;
job_title | n Business Intelligence Analyst | 3 Data Analyst | 4 Data Engineer | 3 Data Scientist | 6 Machine Learning Engineer | 3 Research Scientist | 2 Senior Data Scientist | 3 Senior. Data Scientist - | 2 Sr Data Scientist | 2 Sr. Data Scientist | 2 (10 rows)

下の4行は、本来どれも「Senior Data Scientist」のはずなのに、Senior Data Scientist（3件）・Sr. Data Scientist（2件）・Sr Data Scientist（2件）・Senior. Data Scientist -（2件）と4通りの綴りに分かれています。ORDER BYで並べておくと、似た綴りが隣同士に集まって気づきやすくなります。

HAVINGで「繰り返し登場する値」だけ絞る

HAVINGは「グループ化したあとの絞り込み」でした。3件以上ある職種名だけを見たいときは次のようにします。

SELECT job_title, count(*) AS n
FROM ds_jobs
GROUP BY job_title
HAVING count(*) > 2
ORDER BY n DESC, job_title;
job_title | n Data Scientist | 6 Data Analyst | 4 Business Intelligence Analyst | 3 Data Engineer | 3 Machine Learning Engineer | 3 Senior Data Scientist | 3 (6 rows)
⚠️ WHEREとHAVINGの使い分け：count(*)のような集計結果で絞るときはWHEREではなくHAVINGです。WHEREはグループ化の前に行を絞り、HAVINGはグループ化のあとにグループを絞ります。

2列でGROUP BYすると「同じ職種＋同じ業種」の組み合わせの重複も見つかります。GROUP BY job_title, sector HAVING count(*) > 1を実行すると5組（例：Data Engineer×Information Technologyが2件）が返ります。

🍎 かんたん説明

GROUP BYで「同じ値ごとの山」を作り、count(*)で山の高さを見ます。山が2以上（HAVING count(*) > 1）なら重複。1列だけで山を作れば、綴り違いの山が別々に並ぶので表記ゆれが見つかります。

💻 ミニ練習：繰り返し登場する職種を探す

ds_jobsをjob_titleでグループ化し、2回より多く（3件以上）登場する職種だけを、job_titleと件数nで返すSQLを書いてください（HAVINGを使う）。

SELECT job_title, count(*) AS n
FROM ds_jobs
GROUP BY job_title
HAVING count(*) > 2
ORDER BY n DESC;

集計結果（件数）で絞るのでWHEREではなくHAVINGを使います。結果は6行（Data Scientistが6件で最多）になります。

②

length() で形式の異常を見つける

GROUP BY length(列) で「仲間はずれの長さ」を探す

データが「なんとなく変」なとき、値の長さを数えると異常が浮かび上がることがあります。教科書のListing 10-6では、5桁のはずの郵便番号（ZIP）が、Excelで数値扱いされて先頭の0が消え、3〜4文字になっていました。length()でGROUP BYすれば一目瞭然です。

📊
length(列)でGROUP BY長さごとの件数を出して、分布を眺める
↓
🔎
少数派の長さに注目ほとんどが同じ長さなら、外れた長さが怪しい
↓
🎯
WHERE length(列) < N で怪しい行を取り出す原因を確認してから修復に進む
📖 教科書の例：meat_poultry_egg_establishmentsでSELECT length(zip), count(*) FROM ... GROUP BY length(zip)とすると、3文字：86件・4文字：496件・5文字（正常）：5,705件と分かりました。同じ手順をds_jobsに使います。

job_descriptionの長さを調べる

SELECT LENGTH(job_description) AS len, count(*) AS n
FROM ds_jobs
GROUP BY LENGTH(job_description)
ORDER BY len;
len | n 0 | 1 3 | 2 32 | 2 33 | 3 34 | 1 37 | 1 ...（以下 38〜52文字が続く） (17 rows)

普通の説明文は30文字台〜50文字台なのに、長さ0が1件・長さ3が2件だけ飛び抜けて短いことが分かります。WHEREで取り出してみましょう。

SELECT post_id, job_description, LENGTH(job_description) AS len
FROM ds_jobs
WHERE LENGTH(job_description) < 5
ORDER BY post_id;
post_id | job_description | len 11 | TBD | 3 18 | n/a | 3 29 | | 0 (3 rows)

'TBD'（未定）、'n/a'（該当なし）、そして空文字列''の3件です。空文字列は「値が空」という値であり、NULLとは別物なので、IS NULLでは見つかりません。長さで探す方法が有効な理由はここにあります。

数値の桁数も、TEXTにして数えられる

length()は文字列用の関数なので、数値列はCAST(founded AS TEXT)で文字列にしてから数えます。

SELECT LENGTH(CAST(founded AS TEXT)) AS len, count(*) AS n
FROM ds_jobs
GROUP BY LENGTH(CAST(founded AS TEXT))
ORDER BY len;
len | n 2 | 2 4 | 28 (2 rows)

設立年は4桁のはずなのに、長さ2が2件あります。WHERE LENGTH(CAST(founded AS TEXT)) <> 4で確認すると、post_id 11と18のfoundedが-1（「-」の1文字＋数字の1文字＝2文字）でした。-1は「不明」を表すダミー値（センチネル）です。

📌 length()検査のコツ：①まずGROUP BY length(列)で分布を見る、②少数派の長さをWHEREで取り出す、③原因（先頭0の欠落・ダミー値・空文字列など）を特定してから修復、の順に進めます。会社名（company_name）の長さを見ても12〜30文字に散らばるだけで、長さで異常は見つかりません。「長さが揃うべき列」にこそ有効な検査です。
💡 PostgreSQLでは：length()のほかchar_length()も使えます。この演習アリーナでもどちらも動きます。
🍎 かんたん説明

length()は文字数を数えるだけの関数ですが、「本来は同じ長さのはず」の列ではとても優秀な検査役です。長さの分布を出して、仲間はずれの長さを探しましょう。

💻 ミニ練習：短すぎる説明文を見つける

ds_jobsから、job_descriptionの長さが5文字未満の行のpost_idとjob_descriptionを返すSQLを、LENGTH()を使って書いてください（結果は3行）。

SELECT post_id, job_description
FROM ds_jobs
WHERE LENGTH(job_description) < 5
ORDER BY post_id;

LENGTH()をWHEREの中で使えば、条件に合う行だけを取り出せます。TBD・n/a・空文字列の3行が返ります。

③

列単位のバックアップと安全な修復

ADD COLUMN でコピー → 狭い WHERE で UPDATE → RETURNING で確認

異常が見つかったら、次は直す番です。ただしUPDATEは元に戻せません（COMMIT済みなら特に）。教科書10章は、修正前にバックアップを取ることを強く勧めています。ここでは特に「列単位のバックアップ」を練習します。

(a) 1列だけをテーブル内にバックアップする

ALTER TABLE ds_jobs ADD COLUMN job_title_copy TEXT;
UPDATE ds_jobs SET job_title_copy = job_title;

これでds_jobsにjob_title_copy列ができ、修正前の職種名が全30行ぶん保存されます。後で元に戻したくなったら、逆向きに代入します。

UPDATE ds_jobs SET job_title = job_title_copy;
⚠️ WHEREのないUPDATEは全行に効きます。上の2つは意図的に全行を対象にしていますが、普通の修正では必ずWHEREで対象を絞ります。

(b) 狭いWHEREで直し、RETURNINGで結果をすぐ確認

RETURNINGはPostgreSQL独自の句で、UPDATEした行を、そのままSELECTしたように返してくれます（この演習アリーナでも動きます）。

UPDATE ds_jobs
SET job_title = 'Senior Data Scientist'
WHERE post_id = 15
RETURNING post_id, job_title, job_title_copy;
post_id | job_title | job_title_copy 15 | Senior Data Scientist | Senior. Data Scientist - (1 rows)

修正後の値（job_title）と、バックアップに残った元の値（job_title_copy）が並んで見えるので、間違いにすぐ気づけます。

(c) LIKEの前方一致でまとめて標準化する

表記ゆれのうちSrで始まるものは、別の新しい列に標準名を入れて直すのが安全です。教科書ではcompany_standard列で同じことをしています（WHERE company LIKE 'Armour%'）。

ALTER TABLE ds_jobs ADD COLUMN title_standard TEXT;
UPDATE ds_jobs SET title_standard = job_title;
UPDATE ds_jobs
SET title_standard = 'Senior Data Scientist'
WHERE job_title LIKE 'Sr%'
RETURNING post_id, job_title, title_standard;
post_id | job_title | title_standard 5 | Sr. Data Scientist | Senior Data Scientist 9 | Sr Data Scientist | Senior Data Scientist 19 | Sr. Data Scientist | Senior Data Scientist 23 | Sr Data Scientist | Senior Data Scientist (4 rows)
⚠️ まだ終わっていません：LIKE 'Sr%'にヒットしたのは4件だけです。Senior. Data Scientist -（post_id 15, 28）はSeで始まるので拾えません。前方一致の条件は「拾いすぎ」と「拾い漏れ」の両方を確認しましょう。なおLIKEはPostgreSQLでは大文字小文字を区別しますが、この演習アリーナ（SQLite）では区別しません（PostgreSQLで区別しない検索はILIKE）。

(d) 連結演算子 || で欠けた文字を補う

教科書では、先頭の0が消えたZIPコードをSET zip = '00' || zip WHERE st IN ('PR','VI') AND length(zip) = 3のように条件付きで直しました。同じ手順を、post_idから3桁の求人コードを作る場面で試します。

ALTER TABLE ds_jobs ADD COLUMN job_code TEXT;
UPDATE ds_jobs SET job_code = CAST(post_id AS TEXT);

-- 1桁の行だけに '00' を、2桁の行だけに '0' を足す
UPDATE ds_jobs SET job_code = '00' || job_code
WHERE LENGTH(job_code) = 1;
UPDATE ds_jobs SET job_code = '0' || job_code
WHERE LENGTH(job_code) = 2;

1回目のUPDATEで001〜009の9行が変わり、2回目で10〜30の21行が010〜030になります。最後にSELECT LENGTH(job_code), count(*) ... GROUP BY LENGTH(job_code)で確認すると、全30行が長さ3で揃います。

💡 LPADという近道：LPAD(CAST(post_id AS TEXT), 3, '0')なら左を0で埋めて3桁にする1行で済み、たとえば3→003、12→012になります。ただしUPDATEではWHEREで直す行を限定する考え方が大切なので、まず||とWHERE length()の型を身につけましょう。
⚠️ 順番に注意：先に「2桁に'0'を足す」を実行すると、1桁に'00'を足した直後の行（3桁）は対象外ですが、逆順や条件なしで実行すると3桁の行に余計な0が付いてしまいます。直したい行だけに当たるWHEREが命です。

(e) バックアップは「テーブル」と「列」のどちらが良い？

テーブルのバックアップ列のバックアップ
作り方CREATE TABLE ds_jobs_backup AS SELECT * FROM ds_jobs;ALTER TABLE ... ADD COLUMN x_copy TEXT; ＋ UPDATE ... SET x_copy = x;
守れる範囲全列・全行（ds_jobsなら30行×15列）その1列だけ
復元別テーブルから値を戻す（結合が必要なことも）UPDATE ... SET x = x_copy;で1文
注意点インデックスや主キー制約はコピーされない元テーブルが太る。作業後にDROP COLUMNで片付ける

迷ったら、大きな変更の前はテーブル丸ごとのバックアップ、1列だけの修正なら列バックアップ、と使い分けます。両方取っても構いません。

🍎 かんたん説明

直す前に「コピー」を取っておけば、失敗しても元に戻せます。直すときはWHEREで直したい行だけを指名し、RETURNINGで結果をその場で確認。全行を巻き込むUPDATEは事故のもとです。

💻 ミニ練習：バックアップを取ってから直す

ds_jobsにjob_title_copy（TEXT）列を追加してjob_titleをコピーしたあと、post_id 9のjob_titleを'Senior Data Scientist'に直し、RETURNINGでpost_id・job_title・job_title_copyを返すSQLを書いてください。

ALTER TABLE ds_jobs ADD COLUMN job_title_copy TEXT;
UPDATE ds_jobs SET job_title_copy = job_title;

UPDATE ds_jobs
SET job_title = 'Senior Data Scientist'
WHERE post_id = 9
RETURNING post_id, job_title, job_title_copy;

先に列バックアップを作り、狭いWHERE post_id = 9で1行だけ修正します。RETURNINGで、修正後とバックアップ（Sr Data Scientist）を並べて確認できます。

④

テーブルをまたぐ UPDATE

相関サブクエリ＋EXISTS と UPDATE ... FROM

教科書10章の後半には「別のテーブルの値を使って更新する（Updating Values Across Tables）」という節があります。M6で学んだJOINやサブクエリの発想をUPDATEに持ち込む技です。ここでは、対応表ownership_mapを使ってds_jobs.type_of_ownershipの長い名前を短いラベルにそろえます。

SELECT * FROM ownership_map;
raw_label | clean_label Company - Private | Private Company - Public | Public Nonprofit Organization | Nonprofit Government | Government Subsidiary or Business Segment | Subsidiary College / University | Education Private Practice / Firm | Private (7 rows)
📖 教科書の題材について：教科書（Listing 10-18〜10-19）では、州コードと地域名の対応表state_regionsを作り、WHERE EXISTSのサブクエリで「New Englandの州の会社だけ」に検査期限（inspection_deadline）を入れています。ここでは同じ考え方で、対応表ownership_map（raw_label→clean_label）を使います。

(1) 相関サブクエリ形式

SET句の右辺に、ownership_mapから対応するclean_labelを探すサブクエリを書きます。サブクエリの中で外側のds_jobs.type_of_ownershipを参照するので「相関サブクエリ」（M6）です。

UPDATE ds_jobs
SET type_of_ownership = (
    SELECT clean_label
    FROM ownership_map
    WHERE ownership_map.raw_label = ds_jobs.type_of_ownership
)
WHERE EXISTS (
    SELECT 1
    FROM ownership_map
    WHERE ownership_map.raw_label = ds_jobs.type_of_ownership
);

なぜ WHERE EXISTS が必要か

ds_jobsの30行のうち、ownership_mapに対応があるのは27行で、対応がないのは3行（post_id 11の'Unknown'、post_id 18と29の'-1'）です。もしWHERE EXISTSを付けなかったらどうなるでしょう。

-- 危険：WHERE EXISTS が無い
UPDATE ds_jobs
SET type_of_ownership = (
    SELECT clean_label FROM ownership_map
    WHERE ownership_map.raw_label = ds_jobs.type_of_ownership
);
SELECT post_id, type_of_ownership FROM ds_jobs
WHERE type_of_ownership IS NULL ORDER BY post_id;
post_id | type_of_ownership 11 | NULL 18 | NULL 29 | NULL (3 rows)
⚠️ 対応のない3行が NULL に上書きされました！サブクエリは該当行が無いとNULLを返し、WHEREなしのUPDATEは全30行に効くので、元の値（Unknownや-1）が消えてしまいます。WHERE EXISTS (...)で「対応がある27行だけ」を更新対象にするのが安全です。

ガード付きで実行した後の分布は次の通りです。

SELECT type_of_ownership, count(*) AS n
FROM ds_jobs
GROUP BY type_of_ownership
ORDER BY n DESC, type_of_ownership;
type_of_ownership | n Private | 11 Public | 8 Nonprofit | 3 -1 | 2 Government | 2 Subsidiary | 2 Education | 1 Unknown | 1 (8 rows)

Company - Private（10件）とPrivate Practice / Firm（1件）がPrivateにまとまって11件になり、-1とUnknownの3行は手つかずで残りました。

(2) UPDATE ... FROM 形式（PostgreSQL）

PostgreSQLには、JOIN風に書けるUPDATE ... FROM ... WHEREもあります。更新元テーブルをFROMに並べ、WHEREで結合条件を書くだけです。

UPDATE ds_jobs
SET type_of_ownership = ownership_map.clean_label
FROM ownership_map
WHERE ownership_map.raw_label = ds_jobs.type_of_ownership;

結合条件に合う行だけが更新されるので、一致しない3行は自然に対象外になり、EXISTSのガードが不要です。結果は(1)と同じ（27行更新）です。

(1) 相関サブクエリ＋EXISTS(2) UPDATE ... FROM
書き方どのDBでも通りやすい標準的な書き方PostgreSQL（とSQLite 3.33以降）の拡張構文
一致しない行EXISTSを忘れるとNULLで上書き結合条件で自動的に対象外
複数列を更新列ごとにサブクエリが必要SETに複数列を並べるだけ
💡 この演習アリーナでは、(1)も(2)も動きます。ただし更新の前に、SELECT count(*) ... WHERE EXISTS (...)で対象が27行であることを確認する習慣を付けましょう。
🍎 かんたん説明

「対応表を見ながら書き換える」作業です。表に載っている行だけ書き換え、載っていない行は触らない。これを保証するのがWHERE EXISTS（またはUPDATE ... FROM）の役割です。

💻 ミニ練習：対応表で type_of_ownership を標準化

ownership_mapを使ってds_jobs.type_of_ownershipをclean_labelに置き換えるUPDATEを書いてください。対応表にない行はNULLにならないよう、WHERE EXISTSのガードを付けること（27行が更新される）。

UPDATE ds_jobs
SET type_of_ownership = (
    SELECT clean_label
    FROM ownership_map
    WHERE ownership_map.raw_label = ds_jobs.type_of_ownership
)
WHERE EXISTS (
    SELECT 1
    FROM ownership_map
    WHERE ownership_map.raw_label = ds_jobs.type_of_ownership
);

SET句のサブクエリで対応するclean_labelを引き、WHERE EXISTSで対応がある27行に限定します。ガードが無いと対応のない3行がNULLになります。

⑤

DELETE・TRUNCATE・DROP の違い

消す範囲の違いと、トランザクションによる安全策

データを消す操作には4つの強さがあります。教科書10章の表に沿って整理しましょう。

コマンド何が消えるかWHERE元に戻せる？
DELETE FROM t WHERE ...条件に合う行だけ使えるトランザクション内ならROLLBACKで可
TRUNCATE t全行を高速に削除（行ごとの走査をしない）使えないPostgreSQLはトランザクション内なら可
ALTER TABLE t DROP COLUMN c列とその中のデータ―バックアップ列・テーブルがなければ不可
DROP TABLE tテーブル全体（構造もデータも）―バックアップがなければ不可
💡 TRUNCATE t RESTART IDENTITY（連番のカウンタも初期化）はPostgreSQLだけの機能です。演習アリーナではTRUNCATEは全行削除として動きますが、RESTART IDENTITYの意味までは再現されません。

DELETEの前に、まずSELECTでプレビュー

消す前に、同じWHEREをSELECTに付けて「何が消えるか」を確認します。

SELECT post_id, company_name, rating
FROM ds_jobs
WHERE rating = -1
ORDER BY post_id;
post_id | company_name | rating 4 | Open Door Health | -1 11 | Brightside Labs | -1 18 | Harbor Analytics | -1 25 | Riverbend Institute | -1 29 | Cedar Health | -1 (5 rows)

rating = -1は「評価なし」を表すダミー値でした。5行が対象だと分かったので、次はそのDELETEをトランザクションの中で試します。

トランザクションで「試して、戻す」

START TRANSACTION;
DELETE FROM ds_jobs WHERE rating = -1;
SELECT count(*) AS remaining FROM ds_jobs;
ROLLBACK;
SELECT count(*) AS after_rollback FROM ds_jobs;
remaining 25 after_rollback 30

トランザクション中は30行から25行に減っています（5行削除）が、ROLLBACKで全部なかったことになり、after_rollbackは30に戻りました。結果に満足したら、ROLLBACKの代わりにCOMMITで確定します。

⚠️ COMMITした後は戻せません。そして、DELETE FROM ds_jobs;のようにWHEREを付け忘れると全30行が消えます。「SELECTでプレビュー → トランザクション内で実行 → 件数確認 → COMMIT」の流れを習慣にしましょう。
💡 PostgreSQLのSTART TRANSACTIONは、この演習アリーナでも自動変換されてそのまま動きます。
🍎 かんたん説明

DELETEは行、DROP COLUMNは列、DROP TABLEはテーブル全体を消します。取り返しがつかない操作は、まずSELECTで確認し、トランザクションの中で試してから確定しましょう。

💻 ミニ練習：評価なしの行を安全に削除

トランザクション（START TRANSACTION〜ROLLBACK）の中で、ds_jobsからrating = -1の行をDELETEし、残りの行数をSELECT count(*)で確認してから取り消すSQLを書いてください。

START TRANSACTION;
DELETE FROM ds_jobs WHERE rating = -1;
SELECT count(*) AS remaining FROM ds_jobs;
ROLLBACK;

WHERE rating = -1で5行だけを消し、remainingは25になります。最後のROLLBACKで30行に戻ります。

📖 用語集

HAVING count(*) > 1
重複の検出
GROUP BYの後にグループを絞る句。2行以上あるグループ＝重複を探せる。
length()
文字数
文字列の長さを返す関数。書式の異常や空文字列の検出に使う。
RETURNING
更新結果の即時表示
UPDATE/DELETEで変更した行をその場で返すPostgreSQL独自句。
|| (concatenation)
文字列の連結
文字列をつなぐ演算子。欠けた先頭の0を補う修復に使う。
WHERE EXISTS
存在チェック
サブクエリが1行でも返せば真。対応のある行だけを更新対象にできる。
TRUNCATE
全行の高速削除
WHERE無しで全行を消すコマンド。DROP TABLEと違い表の構造は残る。
